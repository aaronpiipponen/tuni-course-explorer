# Capture and normalization

The ingestion package captures the public curriculum source into immutable evidence, then converts a completed capture into the normalized official catalogue in one transaction.

## The source adapter and the capture service

`src/course_explorer/ingestion/source.py` declares the source seam. `CurriculumSource` names the reads the capture consumes: `get_curriculum_periods`, `iter_course_version_refs`, `iter_module_version_refs`, `iter_course_versions`, `iter_module_versions`, `get_course_group_versions`, `get_module_group_versions`, `iter_course_group_versions`, and `iter_module_group_versions`. `CapturedResponse` pairs one request path and its ordered request parameters with the exact response body. `SourceResponse` pairs that evidence with a validated value, and `KoriRequestError` and `KoriContractError` separate a failed request from a violated source contract.

`TuniKoriSource` in `src/course_explorer/ingestion/kori.py` implements the seam over one synchronous `httpx.Client`. The client is built from `KoriSettings`, which pins `kori_base_url` to the canonical anonymous HTTPS base with no user information and never follows a redirect. `_request_json` requires a path that starts with `/api/`, and runs `request_json_with_retries` with `retry_contract_errors=False` and `check_initial=False`, so a malformed successful body is terminal rather than retried and the caller's admission callback owns only the retries. A non-200 status is terminal except a 429 or 5xx status inside the attempt budget, and no error carries response text or a response body.

The adapter refuses every shape it cannot prove.

- `get_curriculum_periods` keeps the source periods whose `activePeriod.startDate` year lies between `KORI_FIRST_ACADEMIC_YEAR` and `CURRENT_ACADEMIC_YEAR`, refuses two periods that share one academic year, and refuses a configured range with a gap.
- A search response carrying an `ERROR` notification is refused, as is a truncated response that carries items or a non-positive total.
- A truncated course or module query is partitioned over `_PARTITION_ALPHABET` up to `KORI_MAX_PARTITION_DEPTH`, and a truncated leaf at that depth is refused. `_validate_search_items` requires every item to name the requested period and, for a course partition, to carry a code matching the partition prefix.
- `_iter_paginated_pages` refuses a page whose `start` or `total` drifts from the first page, a page that makes no progress, a duplicate id inside one query, and an accumulated count above the reported total. `_iter_version_refs` refuses a course id that appears in two disjoint partitions and, when the root query was truncated, a partition union below its broad total.
- `_fetch_exact_batch` refuses a response whose id set differs from the requested ids and a response with a duplicate id. `_validate_group_objects` refuses an item from a different group and a duplicate id.
- `_iter_concurrently` submits one window of `KORI_CONCURRENCY` items at a time and submits the next window only when the consumer advances, so a stopped frontier is never queued.

`capture_curriculum` in `src/course_explorer/ingestion/capture.py` runs the phases. It requires `checkpoint_response_count >= 1`, then `_reconcile_manifest` verifies the stored responses and repairs the database provenance through `CapturePersistence.ensure_run` and `register_responses` in bounded batches. A completed manifest is verified against the run row through `verify_run` and reported as it stands. Otherwise `_seed_capture_state` replays the verified manifest into a `_CaptureState`, `mark_running` transitions the manifest, and the service runs `_discover_catalogue` (the periods response, then the course and module reference queries per period), `_fetch_exact_objects` for the discovered ids that no captured object represents, and `_capture_closure` for the pending typed references. Closure processes the pending set round by round in sorted order, fetching course groups and module groups, so a reference cycle terminates. `_next_controlled_batch` consults the `CaptureBoundary` gate immediately before it consumes from a source iterator, and a rejected gate returns `None` and leaves the manifest in its running state.

The service finishes by verifying the stored responses this invocation added through `RawCaptureStore.verify`, calling `mark_completed`, publishing that completed identity through `ensure_run`, and running the final directory verification. After that final directory verification it runs the completed-state `verify_run` against the stored manifest and run row, and the same completed-state `verify_run` runs when an already completed manifest is reconciled. A real error marks the manifest failed with the exception type only and re-raises, except that an error after completion propagates as it is and a failure-state persistence error is raised as an `ExceptionGroup`. `CaptureReport` carries the run id, the status, the manifest path, the response count, the distinct course and module object counts, the two unresolved group counts, and the selected period count.

`_CaptureState` and `src/course_explorer/ingestion/references.py` own reference discovery. `extract_course_references` reads the compulsory and recommended formal prerequisite groups and the substitution options, and `extract_module_references` walks the typed rule tree through `CompositeRule`, `CreditsRule`, and `CourseUnitCountRule` children. Both refuse a missing or blank group identity, a member type other than `CourseUnit` or `Module`, a mismatched group field, and an unknown rule type. A fetched group with no objects is kept as an unresolved identity of its own type.

## The capture store and stored responses

`RawCaptureStore` in `src/course_explorer/ingestion/manifest.py` is the only writer of capture evidence. The glossary names one captured file a stored response, and the code and its symbols call it an envelope, which the manifest records as `CapturedResponseRecord.response_path`.

`create` resolves the raw data root while refusing a symlinked path component, creates `<raw root>/<YYYYmmddTHHMMSSffffffZ>-<run_id>`, and writes the initial running manifest. `open` resolves the manifest below the raw root while refusing a symlinked component or a name other than `manifest.json`, reads its bytes once for parsing and for the store's `manifest_sha256`, and requires its recorded `raw_root_path` to equal the configured root. Opening binds the manifest and verifies no stored response.

`_write_manifest(manifest_path, manifest)` writes a temporary file in the run directory, fsyncs it, renames the temporary file onto `manifest.json`, and fsyncs the directory, so the manifest is published whole or not at all. It returns the SHA-256 of the serialized payload after the durable publication succeeds. `create` supplies that digest to the constructed store, `open` supplies the digest of the bytes it read once, and `_replace_manifest` revalidates the complete model, assigns the returned digest to the store's `manifest_sha256` after the write succeeds, then installs the candidate and drops the invocation-local verified snapshot when the response list or the status changes.

`checkpoint_responses` refuses a completed run and a checkpoint with duplicate request keys. For a request the manifest already records it requires the identical record and re-verifies that stored response.

A stored response the manifest does not already record goes through `_publish_envelope`, which creates the response directory on first use, refuses a stored response for the same request hash that holds different bytes, writes with `open("xb")`, compares the expected bytes when the file appears concurrently, and overwrites nothing.

`_compressed_envelope` is `gzip.compress(body, compresslevel=9, mtime=0)`, so the same body always produces the same bytes. The response path is `responses/<request hash>-<body hash>.json.gz`, where `_request_hash` hashes the canonical JSON form of the request path and its ordered parameters and the body hash comes from the raw bytes.

`_object_records` requires the stored body to be a JSON list whose `(id, groupId)` multiset equals the validated objects, and `_records_from_raw` records each raw item's position and `json_sha256` in stored order.

`verify(*, start_response_index=0, before_response=None)` is the one verification pass. It clamps the requested index to the contiguous prefix this instance already checked, so a reopened store checks from zero while a same-invocation caller continues past the stored responses it verified. It consults `before_response(completed, total)` before each one and returns `False` without touching evidence when the gate refuses. A failing pass leaves the verified snapshot unset, and the response-directory check runs only when every stored response passed.

`_verify_envelope` refuses a symlinked path, a response path that does not match the manifest's request and body hashes, a missing or corrupt file, bytes that are not the deterministic gzip of the body, a body size or hash that differs from the manifest, a typed body that is not a JSON list, and object positions or hashes that differ from the recorded objects. `_verify_response_directory` refuses a non-file entry, an invalid stored-response name, a corrupt orphan, an orphan that is not deterministic gzip, and an orphan whose body hash does not match its name. A completed manifest additionally refuses a file that is not a stored response, an unreferenced stored response, and a set of stored responses that differs from the manifest.

`iter_responses` verifies the current manifest once and then streams its stored responses, and `iter_objects` walks the responses and yields each object with its record and value. `discover_capture_manifests` returns the `manifest.json` path of every direct run directory while refusing a non-directory entry or a symlink and strictly opening each candidate. `prune_capture_runs` refuses a raw root that overlaps `data/backups`, refuses a retained manifest that is not one direct run's `manifest.json`, validates every entry as a non-symlink directory before removing anything, and deletes every other run directory.

## The manifest

`CaptureManifest` fixes the retained evidence contract. `format_version` is the literal `2`, so a retained manifest of any other version fails to parse. The manifest carries the run id, the status, the start and finish times, the raw root path, the selected periods, the response records, both unresolved identity tuples, the failure type, and the three capture-scope fields `course_version_limit`, `seed_course_version_ids`, and `seed_selection_complete`, which must be empty or `None`.

The validators refuse a bounded or seeded manifest, a running manifest with a finish time or a failure type, a completed manifest without a finish time, a failed manifest without both a finish time and a failure type, a duplicate request key, a duplicate response path, one object identity with two source hashes, a blank or repeated period, an unsorted or repeated unresolved list, a naive or non-UTC time, and a response path outside the versioned stored-response form. `_manifest_json_bytes` serializes with sorted keys and a trailing newline, and encodes each time with microsecond precision and a `Z` suffix.

`CapturedResponseRecord` holds the request path, the ordered request parameters, the response path, the body hash and size, the object type or `None` for an evidence-only response, and its object records. A response with an object type must carry object records of that same type, and an evidence-only response must carry none. `CapturedObjectRecord` holds the object type, the source object id, the source group id, the position inside its response, and the source hash.

## Normalization parsing

`parse_capture(store, *, course_guide_base_url)` in `src/course_explorer/ingestion/normalization.py` validates one completed capture. It requires exactly one periods response, a JSON list body, unique period identities, and a manifest period selection that matches the captured period years. It then replays the objects in stored order and skips a repeated object whose group and hash agree with its first occurrence, while refusing a repeat with a different group or hash.

`_SourceCourse` and `_SourceModule` model the fields normalization owns, and both permit unrelated source fields. A localized field is read as `fi` and `en`. A decimal, integer, or date range refuses a minimum above its maximum. A course membership or a module membership naming a period absent from the captured evidence is refused. A course `code` is required, while a module `code` may be absent or blank and is stored as absent.

A course whose `code` is explicitly null adds its `SnapshotProvenance` to `excluded_null_code_course_versions` instead of producing a version. The official URL is built from the validated `course_guide_base_url` and the percent-quoted source object id, so an id with reserved characters stays one path segment.

Module rules are validated as `CompositeRule`, `CreditsRule`, `CourseUnitCountRule`, `CourseUnitRule`, `ModuleRule`, `AnyCourseUnitRule`, or `AnyModuleRule`, and each shape refuses an unknown field. `_module_rule` maps a composite `require` range to `require_min` and `require_max`, a credits range to `credits_min` and `credits_max`, and a count range to `count_min` and `count_max`, keeps the present languages of a localized description, and numbers children by their position. `walk_normalized_rule` yields a tree depth-first.

`_validate_reference_closure` refuses represented and explicitly unresolved identities that overlap, a course prerequisite or substitution reference that is neither represented nor excluded nor explicitly unresolved, a module reference that is neither represented nor explicitly unresolved, and a module rule node that references an identity outside the corresponding closure. `NormalizationBatch` carries the run id, the periods, the course versions, the null-code exclusions, the module versions, and the two unresolved tuples. `normalize_curriculum` parses the whole capture and then calls `NormalizationPersistence.apply` once.

## The normalization transaction

`NormalizationRepository.apply` requires a positive current academic year and window, loads the completed `IngestionRun`, and checks every batch provenance against the run's source snapshots through `_load_snapshots`, which refuses a missing snapshot or one whose type, object id, group id, or hash conflicts. `_prepare_periods` creates or updates the period rows, and `_ensure_owners` inserts the missing canonical course and module rows, and a course row created by the batch starts inactive and carries the batch's year and window.

`_apply_versions` reconciles one object type. When the stored snapshot hash equals the normalized source hash the version is classified `unchanged` and no row or payload is written. Otherwise the version is classified `changed`, its payload is deleted through `_delete_version_payload`, and its fields are updated in place with the batch's snapshot, so the version keeps its primary key. A source id with no stored row is inserted. The deleted payload is the course text, the period memberships, and the prerequisite and substitution options, or the module rule nodes and period memberships. `_insert_version_payload` writes those shapes back, with `_insert_rule_tree` writing one node per tree node. An exact source id linked to a different canonical group raises `ValueError`.

`_remove_excluded_null_code_versions` deletes the stored version of every excluded source id and then deletes the canonical course when no version of it is stored. `_recalculate_courses` rewrites the first and last listed academic year, the active flag through `is_within_activity_window`, and the stored year and window for every affected group. The report then compares `select_representative_source_ids` before and after the batch to count `representative_changed_course_count`, returns the exclusion provenance, and counts the `new`, `changed`, and `unchanged` classifications per object type.

The whole batch runs inside one `session_scope` transaction, so any raise rolls back every row the batch wrote.

## Composition and lifecycle entry points

`src/course_explorer/ingestion/importing.py` composes the two services. `import_curriculum` runs `capture_curriculum` and returns `None` when the controller paused or stopped at a durable boundary. It consults the gate once at `before_normalization` and then runs the one normalization transaction with no further polling, splitting, or interruption. `CurriculumImportReport` validates that both services report one run id, that the capture completed, that `course_object_count` equals the normalized version count plus the null-code exclusions, that `module_object_count` equals the module version count, and that both unresolved counts agree.

`src/course_explorer/ingestion/commands.py` wires validated settings into that service. `run_capture_command` loads the capture, normalization, Kori, and database settings, opens the retained store when `resume_manifest` is given and creates one otherwise, calls `on_store_selected` immediately after the store exists so a detached worker can bind durable state to the manifest identity, and refuses a negative `verification_start_index`.

`IngestionStage` in `src/course_explorer_admin/local_stages.py` adapts the command to the lifecycle. `select_options` adopts the sole retained running or failed manifest for a bare start and refuses two candidates. `identity_sha256` hashes every source, request-shape, and normalization value that changes captured work: every Kori setting except the four operational tuning values `kori_request_timeout_seconds`, `kori_max_attempts`, `kori_retry_backoff_seconds`, and `kori_concurrency`, together with every normalization setting, through `ingestion_configuration_sha256`. The raw-data root and the capture checkpoint frequency are capture settings, and the hash takes no capture setting.

The stage records the selected store's published `manifest_sha256`, its relative path, and its run id, resets the recorded verification prefix when that digest changes, reports the capture stage, the response counts, the verification counts, and the normalization stage through its progress, and retains the manifest identity that the next bare start continues from.

## Tests

`tests/ingestion/test_capture.py` proves deterministic gzip bytes, canonical response paths, atomic manifests with no temporary file left behind, raw position replay, one typed closure visit per group, unresolved group retention, a rejected boundary before the network pull, a completed capture refusing an unexpected file, and the completed-manifest checkpoint before the final directory check, and the store's published digest matching the manifest bytes through create, capture, and open.

`tests/ingestion/test_capture_recovery.py` proves that a reopened failed resume re-checks its retained prefix and fetches only missing evidence, that a failed batch publication leaves exact orphans which one retry adopts, that changed or corrupt evidence is never overwritten, the failure lifecycle and the `ExceptionGroup` for a failure-state persistence error, and `discover_capture_manifests` refusing a symlink or a broken manifest, with an opened store's digest matching the manifest bytes.

`tests/ingestion/test_capture_repository.py` proves idempotent provenance reconciliation and the refusal of a conflicting or extra snapshot row. `tests/ingestion/test_normalization.py` proves the blank module code, the missing course code refusal, the quoted source id in the official URL, first-occurrence deduplication, and the malformed and incomplete evidence refusals.

`tests/ingestion/test_normalization_repository.py` proves the idempotent round trip through the normalized database digest, the in-place rewrite of a changed version with disjoint payload identities, the `unchanged` classification keeping a row and its primary key, the unbounded credit maximum, and the report counts. `tests/ingestion/test_normalization_recovery.py` proves null-code exclusion, a retained coded sibling, the canonical identity conflict refusals, the full rollback on a conflict, and the retained provenance of an exclusion.

`tests/ingestion/test_import_repository.py` proves the composed boundary gate, the retained-verification resume from a reopened store, and the idle cleanup that keeps the retained evidence.

The source adapter itself is covered by `tests/ingestion/test_kori_source.py`, which drives `TuniKoriSource` over an `httpx.MockTransport` and proves the exact request parameters, the partition and pagination rules, the exact batch id set, the group response validation, the bounded concurrency windows, and a request error that carries no response text.

A change to the capture phases belongs in `capture_curriculum`, a change to the stored-response layout or its verification belongs in `RawCaptureStore`, and a change to the write rules belongs in `NormalizationRepository.apply`.
