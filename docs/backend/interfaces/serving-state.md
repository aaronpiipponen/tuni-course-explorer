# Serving state

The serving state is one resolved dataset identity, its opened artifact build, and the retained caches that the supervisor creates before it forks the worker processes.

## The serving dataset identity

`read_dataset_role(state_root, role)` in `src/course_explorer/datasets.py` memoizes each role's parsed receipt by the state root, the pointer's modification time and size, and the receipt's modification time and size, so the same pointer and receipt files reuse the model and either file's rewrite re-reads it. Only the receipt model is reused, and `clear_dataset_cache()` drops both roles as part of `clear_configuration_caches()`.

`resolve_serving_dataset()` in `src/course_explorer_web/dataset.py` is the one serving-identity owner. It resolves the database and its Selected receipt together through `load_database_settings_with_identity(role="selected")`, requires the nonempty `COURSE_EXPLORER_WEB_GENERATION` process value, and hashes `[generation, selected_dataset_id]` with the product's canonical `json_sha256` and `ensure_ascii=False`. A bootstrap state root with no Selected pointer contributes a JSON null selection, so its identity depends on the generation alone. Only that digest leaves the server: no connection URL, host, database name, password, receipt content or process identity is reported. A missing generation value raises at the read boundary, so a serving process that was not started by the entry point fails its first cached read instead of serving without an identity.

The supervisor creates the generation once, and every front router and worker process it starts inherits it. A unit restart creates a fresh value, so a restarted supervisor reports another identity for the same Selected dataset. [Web supervisor](/docs/backend/interfaces/web-supervisor.md) describes that handoff.

## The retained caches of one identity

Eight dataset handlers use retained state. Search uses the preloaded projection and its token tables, and on a site that serves the embedding features it also uses the packed group count and the shared query-embedding cache. An empty dataset retains a zero group count. The course-summary handler uses the preloaded projection, and the next-course handler uses the shared report cache.

The comparison handler uses the opened set's hub pair, the settings bundle's embedding configuration identity, the preloaded projection and the serving session factory. The recommendation handler runs only on a site that serves the embedding features, where it uses the shared chunk and centroid stores, the shared report cache and the shared centroid lookup. The study-structure handler uses the study fragments, the catalogue handler returns the retained plain or gzip catalogue body of its serving identity, and the prerequisite handler uses the retained engine and the per-worker native fact handle and consumes no artifact field.

`serving_caches(serving)` in `src/course_explorer_web/serving_cache.py` returns the one open serving engine, the supervisor's opened artifact set and its retained facilities, and on a site that serves the embedding features the worker's centroid lookup over the shared store. One module-level slot holds the current set behind one lock. The supervisor fixes one dataset identity for its whole lifetime, so the first request of a worker builds its set and every request of that worker receives the same instances.

The supervisor resolves one `ServingSettings` bundle of the web, search and serving-dataset settings before it forks the workers, and every dataset route reads the members it needs from that bundle instead of loading settings or resolving the pointer per request. On a site that serves the embedding features the bundle also carries the one resolved embedding configuration, the embedding configuration identity derived from it, and the one query-embedding client, so a search, comparison or recommendation request does not hash the settings again and a search request opens no client of its own. On a site with the features off those three members are `None`. A worker that was not forked from a preloaded supervisor raises and rebuilds nothing.

`ServingDatabase` opens `create_database_engine(serving.settings)` and `create_session_factory` when the set is built, and `factory()` returns the one factory the dataset's requests use. `ServingArtifacts.open` resolves the artifact key and opens the current build, so a missing artifact fails at construction. The supervisor calls it once before the fork, and a worker inherits the result rather than opening it again. The serving process exits with its engine open, so no close path exists.

The supervisor builds the lookup projection and creates the report region and, on a site that serves the embedding features, the query-embedding region once before it forks the workers, and every worker reads the inherited objects. A worker started without those preloads raises and rebuilds nothing. A Selected pointer change replaces the whole supervisor, not one worker, so the regions and the projection share the supervisor's lifetime, and such a change reaches serving through the restart that [Operations](/docs/operations/README.md#derived-files-served-data-and-the-web-restart) states.

On a site that serves the embedding features the artifact set maps the configured embedding directory's read-only hub pair, centroid matrix and chunk store, and the current build's catalogue artifact and study fragments. On a site with them off it maps the current build's catalogue artifact and study fragments alone. Each worker's native fact handle retains the canonical facts its requests read. The report cache retains one complete next-course report per canonical request and one alias for each distinct raw request that resolved to it.

`WebSettings` carries the two region sizes. The report region is bounded by `WEB_NEXT_COURSE_REPORT_CACHE_BYTES` and the query-embedding region by `WEB_QUERY_EMBEDDING_CACHE_BYTES`. File-backed artifact pages and the native fact handles are charged to the worker cgroup and are not part of the Python share.

The launcher sets `MALLOC_ARENA_MAX` from `WEB_MALLOC_ARENA_MAX` for the supervisor it execs, and the front router and every forked worker inherit it. glibc creates at most that many malloc arenas per process, so a worker retains less free heap after a burst of concurrent requests.

The example sets 100663296 report bytes and 50331648 query-embedding bytes.

## The artifact set and the catalogue artifact

`ServingArtifacts.open` resolves the artifact family, the current build and, on a site that serves the embedding features, the embedding directory of the running configuration. It maps that directory's hub pair and shared centroid and chunk stores, maps the current build's study fragments, and reads the packed search meta row once for its group count. A dataset whose packed search meta row exists and whose stored neighbour table holds no row fails the open, so a served dataset with vectors always carries its neighbour rows. The opened set holds that group count alone, so no request reads or verifies the meta row.

A missing embedding directory for the running configuration refuses the open with the build guidance. A hub file holds either one finite vector of `COURSE_EMBEDDING_DIMENSION` components or, for an empty dataset, an empty array. A hub file that is not a JSON array, or a nonempty hub of another length, with a non-numeric component or with a non-finite component refuses the open with the same guidance. An empty catalogue hub with no meta row opens the zero retained group count of an empty dataset, and a missing meta row beside a nonempty catalogue hub refuses the same way. On a site with the features off it reads the current build's catalogue artifact and study fragments alone and holds no embedding read. [Serving artifact build](/docs/backend/text-and-vectors/serving-artifact-build.md) describes the files and the build that writes them.

The supervisor opens the set once before it binds any listener or forks a worker, through `preload_serving_artifacts()`. That one opening appends the serving identity to the catalogue artifact and compresses the result, and every forked worker inherits the set and both bodies. A worker's first request builds only its own retained engine and, on a site that serves the embedding features, its centroid lookup over the inherited shared store.

### The catalogue artifact

`POST /api/catalogue` answers from the inherited body rather than from a command report. The supervisor builds two bodies once per supervisor: the plain body with the dataset identity already appended, and the gzip form compressed from that body. A client whose `Accept-Encoding` admits `gzip` with a positive weight receives the gzip body with `Content-Encoding: gzip` and `Vary: Accept-Encoding`. Every other client receives the plain body from the route, and the catalogue route adds no `Vary` header to that answer, because `GZipMiddleware` adds that header to a response it may compress and a second value duplicates the header. A request whose header names gzip with a zero weight still reaches `GZipMiddleware`, whose own test of the header can compress that plain body.

Both bodies live in the serving process's memory. The build directory holds the plain catalogue artifact alone and no compressed copy, so an encoded answer performs no file read, and a restart reads the build's plain artifact again. The plain artifact is generation-independent.
