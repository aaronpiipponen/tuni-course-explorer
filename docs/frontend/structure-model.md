# Structure model

The structure model projects each official report into display rows and resolves the profile's ordered programmes, choices and places into one rendered tree.

## Programmes and the forest

`web/src/features/structure/model.ts` holds the pure projection. It normalizes an official rule tree into nodes, options, and rule groups, and it derives every key from the position of the rule among its siblings.

`programmeKey(groupId)` returns `p:<encodeURIComponent(groupId)>`, the browser node-key prefix of one top-level programme. The prefix is a key, not a new entity identity, and the canonical module identity stays the programme identity everywhere else.

`buildProgrammeForest(reports, language = "en")` projects the supplied reports in their given order with `buildStructure(report, programmeKey(report.root.module.group_id), language)`, stamps each direct entry's kind as `programme`, appends the `UNPLACED_KEY` (`u`) bucket, and returns one transparent `$structure` wrapper. The bucket rule reads `any studies` and its title reads `Unplaced studies`. The forest's direct entries are its ordered programmes, and no education title or header is drawn. Programme kind comes from that position alone, so a top-level bare module is a programme row and a report nested elsewhere is a module.

`buildStructure(report, key = "r", language = "en")` builds one module node from the report's root. The root rule key is `<key>/<sibling_position>` when the root rule is a non-mandatory composite, a credits rule, or a course-unit-count rule, and `<key>` otherwise.

`moduleNode(module, key, language, ruleKey)` builds one module node:

- The node kind is `module`. The official `DegreeProgramme` type grants no interaction kind, so every nested caller of `moduleNode` produces a module node. The type selects display nouns alone, through `nodeWordingKind` in `presentation.ts`.
- The rule label is the target-credit range when the module carries target credits, an empty label for an unrestricted `AnyCourseUnitRule` or `AnyModuleRule`, and `ruleLabel(module.rule, language)` otherwise.
- The entries come from `project(module.rule, ruleKey, ruleGroups, key, [], language)`.
- When the module rule is a `CourseUnitRule` or a `ModuleRule` and the projection produced no rule group, `requiredRuleOptions(entries)` turns its entries into one required group whose `requiredCount` is the option count.

`ruleLabel(rule, language)` reads a `CompositeRule` as `all required` or a choose range, a `CreditsRule` and a `CourseUnitCountRule` as `range(min, max, unit, language)`, `AnyCourseUnitRule` as `any course`, `AnyModuleRule` as `any module`, and `CourseUnitRule` plus `ModuleRule` as `required`. Any other node type throws `Unsupported structure rule type`.

`project(rule, key, ruleGroups, ownerKey, choicePath, language)` walks one rule. A child key is `<key>/<sibling_position>`, and the branch decides the shape:

| Rule | Result |
|---|---|
| `CourseUnitRule` with a course | A `course` entry stamped with the origin |
| `CourseUnitRule` without a course | A `note` entry from `reasonText(rule.unresolved ?? "course_not_represented", language)` |
| `ModuleRule` with a module | A nested module node whose rule key is `<key>/<module.rule.sibling_position>`, stamped with the origin |
| `ModuleRule` without a module | A `note` entry from `reasonText(rule.unresolved ?? "module_not_found", language)` |
| `AnyCourseUnitRule` or `AnyModuleRule` | No entries |
| All-mandatory composite | The projected children in order, one required group from `requiredRuleOptions`, and the nested groups |
| Composite whose `require_min` equals its child count and whose `require_max` is null or at least that count | One transparent group holding the projected children, one required group, and the nested groups |
| Positive credits or count rule with one all-mandatory composite child | The child's entries, one required group carrying the credit minimum, and the nested groups |
| Positive credits or count rule whose single child is a composite with one all-mandatory grandchild | That grandchild's entries, one required group, and the nested groups |
| Any other composite, credits rule, or count rule | A `choice` node |

A `choice` node takes its options from the child projections that carry entries. Its `single` flag is true when the option rule is a composite with `require_max` of 1, its title names the option count with the noun its option entries share, which is courses, degree programmes, other modules, or options when the entries differ in kind, and `autoSelectSingleWrapper` is true when one option holds one nested choice. A rule group is added for a choice that holds a selectable entry, is not auto-selected, and whose `requiredCount` comes from `require_min` for a composite or from zero otherwise.

`setOptionOrigin` stamps the entries of each option with `ownerKey` and the choice path, extends the path through a nested choice, and keeps the leaf owner of a transparent wrapper. `hasSelectableRuleEntries` decides whether a group's options hold anything a reader can choose, and `requiredRuleOptions` flattens a transparent wrapper and skips a nested choice.

## Display nouns and the node kind

`web/src/features/structure/presentation.ts` owns the words a node shows. `nodeWordingKind(node)` returns `programme` for a node whose positional `kind` is `programme` or whose module carries the official `DegreeProgramme` type, and `module` otherwise. `nodeKindLabel(node, language)` translates that result for a programme or module node, and the positional kind for a choice, a group or the bucket, so the row kind label and the drawer header name a nested degree programme as a programme. The drawer footer, the drawer empty text, the reset question title, the removal question title, the reset notice and the two destination notices read the same result.

The result selects words alone. It never changes a node's `kind`, its place in the forest, its controls or its actions, so a nested degree programme keeps the drawer, the search, the reset and the removal of a module.

## Resolution, precedence and single render

`resolveStructure(root, edits, content, language)` returns a `ResolvedNode` tree. It walks once with `seenCourses` and `seenModules`, the latter seeded with the root module identity, so a course or module named in two branches is shown once.

- For a choice node the visited entries are the entries of the options in `edits.choices[node.key]`. An `autoSelectSingleWrapper` node with no stored option uses all of its options instead. The `chosen` list records the options in force.
- A `course` entry whose `edits.coursePlacements[id]` is a string other than the node key is pushed to `removed` and not shown, and so is an entry with a `null` placement. Every other occurrence of the identity is suppressed by `seenCourses`.
- A `node` entry with a module follows the same precedence through `edits.modulePlacements[id]` and `seenModules`.
- The place overrides act before first-occurrence deduplication, so a recorded place wins over the first official occurrence of the identity.
- A module identity that a forest holds as one of its direct programmes is reserved against the nested occurrences of the same module, and the direct entries are visited in list order, so a top-level programme cannot disappear because another programme also references it.
- After the entries, every `edits.coursePlacements` entry whose target is this node, whose entity the node does not already hold, and whose identity is not shown is added from `content.courses` with `added: true`, and a missing summary throws `Missing placed course summary`.
- The same pass over `edits.modulePlacements` builds the added module through `buildStructure(report, "<key>/m:<id>", language)` and throws `Missing placed module report` when the report is absent.
- Added content therefore comes only from the placement maps, so a placement that names no visited node is shown nowhere.

`officialHomes(root, edits, content)` records every node key where the official tree names each course and module identity, and for each stored module placement with a string target and a report it walks the projection of that module as well.

`indexResolved(root)` walks the resolved tree into `byKey`, `courseAt`, and `moduleAt` maps. `nextChoices(choices, node, optionKey)` sets the sole option for a `single` node and returns the same object when it is already that option, and toggles the option otherwise. `displayContents(resolved)` flattens a choice or transparent child into its parent, so the drawn tree holds no empty wrapper row.

## Placement edits, the later addition and scoped reset

`web/src/features/structure/edits.ts` holds the pure placement edits.

- `place(edits, field, homes, id, target)` deletes the old entry of the identity, writes the target when it is not null, and writes a `null` target only when the identity has an official home. An identity with no official home is dropped instead, so nothing dangles. `placeCourse` and `placeModule` bind the course and module fields.
- `insideScope(scopeKey, key)` answers whether a key is the scope key itself or sits under it, and `resetScope` uses it to drop the choices whose key is inside the scope and the placements whose target is inside it or whose official home is inside it.
- `moveScope(edits, content, from, to)` rewrites the records one moved scope owns for the node keys it renders at in its new place.

  The two renderings come from the same official rule and the same placement records, so `scopeKeys` pairs their nodes and their choice options in the order the rule names them, pairs a module a record places inside the scope by identity, and reads each key from the projection on its own side, because a module's contents take their keys from the rule key of its own root rule rather than from a plain extension of its node key. A pair that does not line up raises `A moved scope does not match its new place`.

  A record under the moved node key that no paired node names holds a place the new rendering does not have and leaves the state, a choice key and a placement target take their paired key, and a removal or a placement outside the moved node describes an identity and stays as it is.

  `replacedScopeHomes(homes, movedKey)` returns the official homes the clearing of a replaced scope reads, with the homes of every identity the moved subtree names removed, so the clearing keeps the removals and the places of the subtree that moves out of it while the replaced programme's own records clear with it.
- `hasScopedEdits(root, edits, content, scopeKey)` resolves the forest with the stored edits and again with the candidate `holderPulls(root, edits, holderNode, content, false).edits`, which is the state a held identity shows when its own place draws it with its own official defaults, and compares the two targets as `scopeValue` tuples. The current target must resolve or the call raises `Structure target is unavailable`, and a candidate that does not render the target counts as a difference. A tuple holds the node key, the module identity, the rendered course identities, the notes the projection shows and its children tuples, so a record that leaves the rendered contents unchanged, such as an empty choice list, a chosen option that renders the same contents, or a place at an official home, is not a difference, and neither is a course the candidate pulls out of another holder into the scope. `Homes` is the exported map type the placement helpers share.
- `holderPulls(afterTree, afterEdits, holderNode, content, present, pull = true)` returns the next edits of one added holder and the courses that move with them. The holder node is resolved on its own rule, so each record is the holder's own first place for a module or a course it officially renders, and the module records name the node whose entries render the module.

  The `present` flag is whether the tree renders the holder before the operation's own writes, which means the operation moves the holder. A moved holder returns `afterEdits` and an empty move list, so the whole current subtree it holds travels untouched: a removed identity stays removed, a course it renders elsewhere inside its own scope or directly in the `u` bucket keeps that place, an official course another programme or module renders stays there, and no module takes its official place again. A holder the tree does not render adopts its scope's official defaults, because the records `clearScope` drops from that scope are removed before the restoration, and a module the cleared projection renders nowhere takes its official place again, which brings the courses inside it with it.

  A place or a removal outside the holder stays as it is, because the clearing touches only records whose key or target is inside the holder, so the holder restores only the official identities that render nowhere. The courses are read against a projection that includes those restored module records, and a course the cleared projection does not render at its own node takes the place of that node again.

  The move list reads the tree before the scope's records are cleared, so a course of the holder's own rule that the tree renders outside the holder is listed as a move from the node the tree shows there and takes the holder's own place, while a course that renders nowhere or that renders directly in the `u` bucket is not listed and keeps its place.

  `pull` is whether the listed courses move in: a kept course keeps the record it holds and no place is written for it, so the node outside the scope renders it exactly as it does now and the adopted official contents render without it.
- `keepCoursePlacements(edits, previous, pulls)` returns edits with the placement record of each listed course as the previous edits hold it, and with no record for a course that holds none. A scope clear drops the record of a course whose official home is inside the cleared scope, which is what returns that course to the scope, so this is the owner that keeps such a course where it is: `holderPulls` reads it for a kept addition, and the reset owners read it for a kept reset.
- `scopePulls(root, edits, content, scopeKey)` returns the courses one scope's reset returns to it from the nodes that render them now. It resolves the tree with the stored edits and again under `resetScope` for that scope, and a course that renders outside the scope in the first projection and inside it in the second is listed with the node that renders it now. A course that renders directly in the `u` bucket is not listed, and a course another node renders through the official rule rather than through a record of its own is not returned by the clearing and is not listed.
- `placeModuleWithCourses(root, edits, content, moduleId, targetKey, from?, pull = true)` places the module, resolves the tree to find the destination node of that module, and returns `holderPulls` for that destination together with the next edits. Its `from` node is the pre-operation rendering of the module in the caller's own tree, which `modulePlacement` reads from the tree the choice extension has not reached yet, an omitted node reads the module of the supplied edits, and a rendered module moves with its subtree through `moveScope` before the placement resolves. The courses a module it does not render pulls belong to the caller's confirmation, `pull` decides whether that placement moves them in, and a moved module pulls none.
- `clearedScopePlacements(affected, edits, afterTree, afterEdits, content, clearedKey, touched, completedCourseIds)` returns the records that keep a cleared scope's courses out of the nodes the action does not touch. A course that the cleared scope held through a string placement, and that the next projection renders in a node outside `touched`, is placed in `u` when it is completed and removed from the tree when it is not.

## Selection migration and the shared sets

`web/src/features/structure/actions.ts` holds the only writer that moves the structure slice and the shared course sets together.

`applyStructure(store, change)` runs the callback inside `store.updateCurrent` with the current profile state. A callback that returns `null` leaves the state as it is and writes nothing. Otherwise the returned `next` structure and its explicit identities migrate the shared sets:

1. A course named by `state.structure.placedCourseIds` that the next projection does not hold, and that is not completed, is dropped from the selection.
2. An identity of `discardUncompletedCourseIds` that is not completed is dropped as well.
3. An identity of `removedCourseIds` leaves both course sets, so the removal of a completed course takes its completion with it.
4. The selection that is left keeps its order, and every identity of `next.placedCourseIds` that is absent is appended.
5. The structure slice is written as the next programme list, choices, course placements, module placements, and placed identities.
6. `pendingSisuImport` is written from the change when the change supplies it and kept as it is when the change omits the field, so one write places a pending capture and clears it together.

A completed course is never dropped by steps 1 and 2, which is what keeps a completion across a programme replacement, a reset, and a module deselection. An explicit removal is the operation that drops it.

`programmeOutcome(state, operation, content, completedCourseIds, pull)` is the one owner of the programme operations. It computes the next programme list, the scoped edits, the pulled courses and the uncompleted discards of one `ProgrammeOperation`:

- `{ kind: "add", groupId }` refuses a programme the list already holds with `Programme is already added`, appends the identity, and adopts the appended programme's official defaults while it records the courses that programme pulls. A programme another node of the tree displays moves to the list with its whole current subtree, which `moveScope` rewrites for the top-level key. The addition drops that programme's own placement record before the after tree resolves, because the ordered list renders the identity and a record, a removal record included, would suppress its entry.
- `{ kind: "replace", groupId, replacementGroupId }` keeps the affected position, refuses an identity that another top-level position holds, reads the replacement node of the state that starts the operation, clears the old scope with `resetScope`, and records the courses the replacement pulls.

  A replacement programme that the tree already displays keeps its own subtree: `moveScope` rewrites its records for the top-level key and the clearing reads the official homes without the keys of the moved node, so the moved choices, additions and removals survive while the replaced programme's own records clear around them, and the replacement's own placement record is dropped before the after tree resolves, because the ordered list renders the identity and a record, a removal record included, would suppress its entry.

  A replacement the tree does not display adopts its official defaults, and its clearing and its adoption both read the edits that already dropped that record, so a removal record of that identity does not suppress its top-level entry.
- `{ kind: "reset", groupId }` applies the clearing outcome with the same identity, and it lists the courses that clearing returns to the scope through `scopePulls`.
- `{ kind: "delete", groupId }` removes the identity and clears the same scope, and it works for the last programme.
- A missing programme or a report the content lacks raises `Programme is unavailable`, and no branch fetches, falls back or writes.

`changeProgrammes(store, operation, content, removeCompletedCourses = false, pull = true)` runs that outcome inside `applyStructure` and writes the full next structure with the uncompleted discards of the affected programme. Its `removeCompletedCourses` flag is the destructive choice of the entry point that offers one. For a delete it is **Delete all**: the affected programme's completed courses join `removedCourseIds`, which takes them out of both course sets, and a `null` placement takes them out of the tree so no surviving programme brings them back. For a reset it is **Reset all**, which passes the prepared ordinary change to `resetCompletionChange`. An ordinary reset and every delete without the flag write the ordinary change. Its `pull` flag is whether the addition, the replacement and the reset move the listed courses in, and a kept reset keeps its listed records through `keepCoursePlacements`.

`resetCompletionChange(state, scopeKey, content, ordinary)` adds the destructive reset outcome to one prepared ordinary reset change. It resolves the pre-reset forest from the callback's state and requires the target node, raises `Programme is unavailable` or `Structure target is unavailable` when either is absent, and reads `removedCompleted` as the intersection of that node's subtree identities with `state.completedCourseIds`, so only a completion the scope actually holds is cleared.

It copies the ordinary change's course placements and leaves its choices, module placements and programme list as they are. A restored placement is kept when the candidate projection locates that identity inside `scopeKey`, and set to `null` otherwise, so a discarded completion cannot fall back into an untouched holder and a restored mandatory course is selected.

It returns the ordinary change with the final placement map, the final placed identities, and `removedCourseIds` equal to `removedCompleted`, and it preserves the ordinary change's uncompleted discards and pending-import field. `applyStructure` removes `removedCourseIds` from both course sets before it appends the placed identities, which is the order that selects a restored mandatory course as uncompleted.

`programmeMoves(state, operation, content)` returns the listed moves of the same outcome, so an interface confirms them before the write and a cancelled confirmation writes nothing, and it answers a reset with the courses that reset returns to its scope through `scopePulls`. `displayedPlace(state, content, groupId)` returns the localized node that displays one identity of that state, and a direct `u` bucket entry answers with no node because that bucket holds unplaced items by definition.

`resetUnplaced(store, content)` resolves the forest, collects the courses of the `u` subtree and the selected courses outside the whole forest, drops the `u` choices, keeps a placement whose target is outside the bucket, turns a placement into the bucket into `null` when the identity has an official home outside it, and commits the resulting projection with the collected identities as uncompleted discards.

`removeFromSelection(store, courseId)` drops the identity from both course sets.

## Pane hooks, dialogs and programme operations

`web/src/features/structure/StructurePane.tsx` composes the tab:

- The pane reads the ordered programme identities, the choices, the two placement maps and `pendingSisuImport` from its profile selectors, and `usePlacedContent(courseIds, moduleIds, allowUnrepresented)` is the one hydration owner. It receives every selected identity and every string course place, every programme identity and every string module place, so the programme reports and the placed modules and courses arrive through one effect.
- The pane builds the forest from the programme identities when those reports exist. `projection(ids, edits, content, language)` returns `null` while the hydrated content lacks a programme report, the report of a placed module, or the summary of a placed course, and the pane holds the last complete programme list, edits and content in that time, which re-projects that input in the live language instead of blanking the tree. It renders the hydration failure and the editor's failure as `ErrorNotice`, so a refused operation reads in the profile language.
- A reconciliation effect runs inside `applyStructure` with the latest state. It returns `null` when the derived placed identities already equal the stored ones, and `null` as well when the hydrated content lacks a report the identity list needs, which leaves the hydration owner to load it.
- While `pendingSisuImport` is not null the pane reads with `allowUnrepresented`, runs no ordinary reconciliation, and holds the structure loading state, so no editing surface reaches the pre-resolution choice maps. One effect captures the current profile identity, refreshes the saved envelope and returns when that identity moved, resolves the capture from the callback's own state inside `applyStructure`, and holds the returned issues in one transient notice. A failure renders its `ErrorNotice`, keeps the pending record and applies nothing.
- `SisuImportNotice({ issues, onDismiss })` renders the issues of one placement as an animated shell above the tree, each with its localized reason and its code or name, and it is visible until it is dismissed or unmounted.
- `useProgrammeActions(content, extend, confirmMoves)` owns the Add and Replace reads. It captures the profile identity and the programme list, awaits the chosen report, refreshes the saved envelope, refuses an incompatible list or profile, and calls `changeProgrammes`. Its `moves(operation)` reads a `ProgrammeMovePreview` through the operation's own report: the holder identity, the pull list of the operation together with the node that displays its holder through `displayedPlace`, and Add asks for the move confirmation first when either exists and refreshes the captured profile and programme list again after the answer, so an Add whose list changed while it waited is refused before the write. Its `run(operation, removeCompletedCourses = false, pull = true)` writes the `pull` mode its caller answered, and an Add whose own confirmation answered `keep` writes with `pull = false`. Reset and Delete use the loaded content through the same call.
- `useStructureEditor` owns the mutations. `commit(updateEdits, ctx, removed, nextProgrammes)` derives the next edits from the latest state inside `applyStructure`, resolves the projection from the ordered programme list that `nextProgrammes` returns when the caller supplies it, so an operation that takes an identity out of that list writes the reduced list together with its edits, requires the target of a node-key action to be present in the latest resolved forest, and raises `Structure target is unavailable` when it is not.

  `choose` writes the next choices through `nextChoices`. `addCourse` extends the placed content with the summary and places the course, and it reports `Already in this module`, or `Already in this programme` at a programme-worded destination, when the course already sits there. `selectRuleCourse` writes the options of the choice path and then the place. `toggleRuleCourseCompleted` places the course when it has no place and then toggles the completion. `deselectRuleCourse(course, removeCompletion)` takes the place away and names the identity in `removedCourseIds` only when the completion goes with it, and a loose completed course whose completion is kept returns without a change.

  `hasNodeEdits(node)` reads the open profile's structure from the store, derives the forest and answers `hasScopedEdits(forest, current, content, node.key)`, so the drawer asks before a removal whose current contents differ from the contents its own place draws with its own official defaults. `resetPulls(node)` reads the same stored structure and answers `scopePulls` for that node key, so the drawer can ask about the courses one reset returns before it writes.

  `resetNode(node, removeCompletedCourses = false, pull = true)` calls `resetUnplaced` for the bucket and writes a full change through `applyStructure` for any other node, so its scoped edits and its completion clearing both come from the same latest profile state inside the callback. It writes the ordinary change for **Reset** and returns `resetCompletionChange` for **Reset all** in every state, so a scope that holds only completions and no change still clears them, and its `pull` flag keeps the courses that `scopePulls` lists in the nodes that render them now through `keepCoursePlacements`.

  Its notice reads `Programme reset to its official contents` or `Module reset to its official contents` from the wording kind of its target. `commit` is the owner of every other editor mutation.
- `modulePlacement(current, ctx, module, targetKey, item, pull = true)` is the pure preparation of one module operation. An official selection extends the choices along the item's choice path first, and a searched addition keeps them. The module identity's destination inside itself raises `A module cannot be added inside itself`, a target the candidate forest lacks raises `Structure target is unavailable`, and the result holds the placement edits, the pulled courses, the visible source node and `moveKey`.

  The tree the choice extension has not reached decides whether the tree renders the module before the operation: a module it does not render adopts its scope's official defaults while one it renders moves with its whole subtree, and its node of that tree supplies the source of the move. The source node is the node whose displayed children render the module identity, found through `displayContents`, and it counts as a module move when it is a programme, module or forest-wrapper node other than the destination, so a module held by **Unplaced studies** and a module the destination already renders move without a module sentence.

  Its destination resolution is read from the forest whose ordered programme list omits the module identity, so a module that list holds renders at the destination node and holds no entry at the programme level. Its source can therefore be the forest wrapper, whose node kind is `group`, for which `modulePlaceText` answers **the programme list** instead of `resolvedNodeLabel`.

  `pull` reaches the adoption, and `moveKey` is a transient serialization of the source node key, of the node key the module itself renders at, and of the pulled course identities with the node keys they leave, sorted by identity.
- `finishModulePlacement(module, targetKey, item, ctx, controller, profileId, programmes)` confirms and applies one module operation on the latest structure. It refreshes the saved envelope and returns without a write when the open profile differs from the captured identity. A different programme list raises `Structure programmes changed while adding a module`. A searched addition whose target already renders the module reports `Already in this module`, or `Already in this programme` at a programme-worded destination, and returns.

  It asks `confirmMoves` once when the preview has a module source or a nonempty pull list, reads the answer as the `pull` mode the write applies, honors the abort signal after the answer, refreshes the envelope again, reads the hydration owner's latest in-memory content through `extend({})`, and calls `commit` with a callback that verifies the programme list and recomputes the placement, together with a `nextProgrammes` factory that returns the captured ordered programme list without the module identity, so a module that list holds leaves it as that write lands.

  A recomputed `moveKey` other than the authorized one raises `Structure moves changed while confirming a module` before the write, so a change another tab saved while the question waited reaches the next structure and an incompatible one writes nothing. The added-module notice with its moved-course count follows a successful commit, and a kept course is not reported as moved.

  `addModule` reads the module report into the placed content and then delegates to it, and `selectRuleModule` delegates with its rule item and the owner key of that item, so both entry points share one placement, one confirmation and one write.
- `runModuleOperation(module, targetKey, item, prepare)` holds the lifecycle both module entry points share: it aborts the previous operation, captures the profile identity and the ordered programme list from the store, sets the pending module identity and clears the visible error, reads the placed content through `prepare` or uses the current content, and clears the pending identity in its cleanup. A failure reaches the editor error state unless the operation was aborted or the open profile changed.
- `ProgrammeMenu` renders the row menu. `ProgrammeConfirmDialog` renders the replacement-only named confirmation, whose description applies the replacement with one sentence, states the place that already displays the replacement programme when a node does, carries the pulled courses, and states the outcome of the replaced programme from its completion presence: its customisation is discarded and its uncompleted courses leave the structure, and, while the replaced programme holds a completed course, its completed courses are kept. Its `onConfirm(pull)` answer is **Replace** for a replacement that pulls no course, and a replacement that pulls one carries **Keep** and **Pull** in place of **Replace**, so the answer states whether the listed courses move in.

  `ModuleRemoveDialog` is the shared compact owner of a programme or module removal question and of the shared reset question: its required `operation` prop of `remove` or `reset` selects the removal title with the **Cancel** and **Delete** actions or the reset title with the **Cancel** / **Reset** actions and **Reset all** added while the scope holds a completed course, and its required `holderKind` prop of `programme` or `module` selects the nouns of the title and of the description.

  The description is chosen from the operation, the holder nouns and the completion presence, so it states the ordinary action in every state and the completed-course choice only while the scope holds one. It retains the name, the completion presence, the operation and the holder kind that the question opened with through the closing animation.

  `CourseMoveConfirmDialog` renders one `CourseMoveRequest` under the `CourseMoveAnswer` its actions return, which is `true` for the pulled courses moving in, `"keep"` for the operation applying with each listed course left where the tree shows it now, and `false` for a cancelled operation that writes nothing. A request with a pull list carries **Cancel** at the left and **Keep** and **Pull** at the right, with the list under a sentence that states the choice, and a request without one carries **Cancel** and **Move** under the **Move here?** title, which names the module and the node that holds it through the request's `moduleFrom` formatter, and names **the programme list** when the source node it formats is the forest wrapper.

  `AddProgrammeRow` renders the row that starts one.
- `StructureDrawer` renders the added-course section and the added-module section as one animated shell each with an `AnimatePresence` list, so a removed course or module animates out and the empty section collapses instead of vanishing, and a section stays mounted while its last row leaves. Both follow the shared transition, which changes at once under reduced motion. It keeps its displayed closing target in component state, clears it on the drawer's own transform transition end, and clears it directly when reduced motion is on.

  A module row whose current contents differ from the contents its own place draws with its own official defaults, or whose module holds completed courses, removes it through `ModuleRemoveDialog`, whose ordinary choice keeps the completed courses loose in the `u` bucket and whose destructive choice passes their identities as the removal list. A row whose placement gives it its own official contents, the courses that placement pulled out of another holder included, and that holds no completion removes at once.

  The drawer's reset preserves the pending target and its opener, opens that same component at every press for a programme or module with `operation="reset"` and the wording kind of the pending target, and calls `resetNode` with `false` for **Reset** and `true` for **Reset all**, so a scope that holds only completions still clears them through the **Reset all** it offers. A reset whose `resetPulls` list is not empty asks a second time through the same `CourseMoveConfirmDialog`, and its answer decides the `pull` mode: **Keep** and **Pull** run the reset with that mode, and **Cancel** writes nothing. A scope that holds no completed course and returns a course asks through that pull question alone.

  The drawer's reset and removal completion presence reads the resolved subtree of the pending target against the live completion selector. `MoveConfirmDialog` appears when `courseHome` names another node, and the move runs at once when it does not, which covers a move out of **Unplaced studies**.

  `CompletedCourseDeselectDialog` appears for a completed course and offers the loose move or the removal with the completion, and it offers the removal alone when the course already sits under Unplaced studies, which the drawer passes through the dialog's `unplaced` prop. The drawer reads `editor` through a ref so a formatter created at click time uses the live `courseHome`. A rule row's module option and the drawer search's module result call `selectRuleModule` and `addModule`, whose own confirmation covers the module move and the courses an addition pulls, and the search closes on a selection.
- `useFreeChoiceAdd` binds the shared selected-set writer to the live store, and every course card and both add-all actions add to Unplaced studies through it.

`useNotice` shows one message for 2200 ms and stores a formatter, so the message renders in the language in force when it is shown.

`PickerOverlay` renders its scrim beside the picker and wraps the picker alone in the optional `anchorClassName` wrapper. `StructurePane` renders `PickerOverlay` directly inside `.structure-root-overlay`, which spans the whole pane from its top edge, so the scrim covers every row of the tree, the pane's padding and the strip above the first row, and passes `.structure-root-anchor`, a sticky zero-height element inside the overlay's inline padding that is the picker's containing block, so the picker holds one place in the visible tab area whatever the scroll position of the pane. While a structure drawer is open the anchor narrows to the drawer-aware width and stays centered, so the picker follows the state of the drawer. A pointer press inside an open dialog and the Escape key of an open dialog belong to that dialog, so the **Add programme** picker stays open for the next pick.

## Request handling

`usePlacedContent` runs its own effect keyed on the serialized course and module identity lists and on `allowUnrepresented`, starts one `AbortController` for the identities it is missing, drops a settled result whose controller was aborted, and aborts the controller on cleanup, so a change to either list, a change of mode and an unmount cancel the pending read. It throws `Requested course summary is missing` when the read omits a requested identity in the ordinary mode, records that identity as unavailable in the pending mode, and records a study-structure `ApiError` with status 422 as an unavailable module in the pending mode alone. Recorded identities count as settled for the request, so its `loading` finishes. `extend` merges the courses a supplied report already carries into the same content map, so a projection that adds official default courses to the selection needs no second read.

`useProgrammeActions.run` and the two module operations of `useStructureEditor` prepare their write from the latest state. Each aborts its own previous operation, captures `store.getSnapshot().currentProfileId` and the ordered programme list before its first await, and returns without a write when the signal is aborted.

`addModule` reads the module report with `readStudyStructure` and merges it into the placed content, and `selectRuleModule` uses the report the open rule tree already carries. Both module operations refresh the saved envelope with `store.refreshFromStorage()`, return without a write when the refreshed current profile differs from the captured identity, and throw `Structure programmes changed while adding a module` when the refreshed programme list differs from the captured one, so their result never reaches a different forest.

The move confirmation waits between two such refreshes, the write recomputes the placement inside `applyStructure` from the current profile state, and a recomputed move identity other than the confirmed one throws `Structure moves changed while confirming a module` without a write. `modulePlacement` throws `A module cannot be added inside itself` when the destination sits inside the module.

`errorPresentation` maps these messages, and the projection and resolution messages, to `UI_TEXT` keys, so each failure reads in the profile language.

## The Sisu capture

`web/src/features/structure/sisu.ts` holds the capture boundary and the pending placement.

`validateSisuPlan(value)` is the recursive check of one capture hierarchy. It requires a non-array object, a nonempty programme array of module objects, the exact `course` and `module` discriminants, nullable nonempty string identities, a nonempty course code and name, a nullable module code, a boolean completion, and arrays of children, and it rejects two non-null top-level programme identities that agree because a programme has one top-level place. An unknown field is discarded, a repeated course occurrence is accepted, and every failure raises `Invalid Sisu plan file`.

`parseSisuCapture(value)` is the boundary of one downloaded capture. It requires a nonempty `markup` string, a module lookup record of group-id lists keyed by the status cell identity the page shows, and a course lookup record of `{ code, groupId }` hits keyed by the displayed code.

The markup is parsed with `DOMParser` as data and is never inserted into the document or evaluated, and the identity of every module and course comes from the lookup records alone: a course hit is matched on its exact code and its group ids are de-duplicated, and a module's list of group ids is de-duplicated, so one sole identity is used and zero or several identities leave the item unresolved.

The hierarchy is read from the module element that holds each row of the plan tree: the own name, the own code, the own status identity, and the own direct module and course rows in document order.

A module with the graduation flag carries a degree header, and a top-level header with no graduation flag, no grouping title and no module information control is the education container, whose direct degree rows become the top-level programmes in their displayed order. A capture with no readable programme raises `Invalid Sisu plan file`.

`prepareSisuProfile(capture, name, language)` builds the profile one import creates: the language of the interface at confirmation, one ordered distinct selected identity per non-null captured course, a completion for every identity that any occurrence captured as completed, the resolved top-level programme identities in capture order, and one independent copy of the hierarchy in `pendingSisuImport`. Choices, places and placed identities start empty, and the call reads no storage and sends no request. `BrowserStore.importProfile` then applies the shared trimmed-name, empty-name and duplicate-name rules.

`resolveSisuImport(state, content, unavailable)` returns `null` while no capture waits and while a read the capture needs has not settled: every resolved module identity of the capture, at any depth, needs a report or a recorded unavailable module, and every selected identity needs a summary or a recorded unavailable course. `captureModuleIds(capture)` returns that module list in capture order, and the pane reads it while the record is pending. Otherwise it returns one `StructureChange` and the issues of the placement, and it writes nothing.

- The available programmes are the captured ones whose report the content holds, and they are written in capture order. Each scope reads `officialHomes` again, so a module placed above it contributes its own official homes to the suppression below. A programme whose identity is unresolved or whose report is unavailable is named as an issue, its representable descendant courses are placed in the `u` bucket, and no education wrapper or invented group id is created.
- One walk per programme starts at the `programmeKey(groupId)` node of the forest. For a captured direct course or module it searches the parent's entries and every option through transparent and choice nodes, and it stops at the boundary of a nested module. A match of a course or a module contributes its choice path, selected through `nextChoices` only when a step is absent, and records the matched entry's `origin.ownerKey` as its place. The walk descends into a matched module's node for its captured children.
- A representable captured course outside the parent's official alternatives is placed on the parent module node with `placeCourse`, so it draws the added outline. An unresolved identity is named and left out, and a captured course outside the hydrated summaries is named, left out of the placed identities and removed from both course sets.
- A captured module outside the parent's official tree joins that parent through a `modulePlacements` entry, and the walk descends into the node `buildStructure(report, "<parentKey>/m:<id>")` builds from its own report, so its captured children are placed inside it and its uncaptured official content is suppressed. A module with no report at all is named as an issue, and its representable descendant courses are placed in the `u` bucket rather than a branch of that programme.
- Every official identity of one parent scope that the capture does not hold there is suppressed through a `null` placement, so a default projection cannot select content the capture does not hold. A captured course or module keeps its matched owning key, so a captured deselection or move is preserved rather than turned into a second card, and a matched module a later scope does not capture keeps that recorded place rather than a suppression.
- An identity that one parent scope offers twice, a captured sibling module that the scope offers twice, a choice path step into an already chosen single option, and a captured sibling module whose identity repeats raise `Sisu choice is ambiguous` and the caller writes nothing.
- The returned change holds the next structure, the unavailable captured course identities in `removedCourseIds`, and `pendingSisuImport: null`. It carries no completion, so the callback's own course sets own the completion and a change another tab made while the reads waited is kept, and issues hold one name, a nullable code and one of `unresolved`, `module_not_placed` or `course_not_represented`.

## Where a change belongs

- A rule kind that the tab should render differently belongs in `project` and `ruleLabel` in `model.ts`, together with the display case in `displayContents` when the node should not be drawn as a row of its own.
- A change to how a place is stored, cleared, or discarded belongs in `edits.ts` and in `applyStructure` in `actions.ts`.
- A change to a programme operation belongs in `programmeOutcome` in `actions.ts`, which the write and the move list share.
- A drawer row or dialog to add belongs in `StructureDrawer` with its own component beside it, and an editor operation to add belongs in `useStructureEditor`. Every scoped mutation derives its next edits from the latest state inside `applyStructure`, through `commit` or through the full change a reset builds, so no edit reaches a stale projection.
- A change to what a downloaded capture holds, to how its markup is read, or to how pending choices are placed belongs in `web/src/features/structure/sisu.ts`.
