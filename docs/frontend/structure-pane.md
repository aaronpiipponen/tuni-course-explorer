# Structure pane

The structure pane hydrates the reports the tree needs, projects one display input, reconciles the placed identities, and hosts the drawer, dialogs and programme operations.

## The pane's one display projection and reconciliation

`StructurePane` keeps one display input: the ordered programme identities, the profile edits, the placed content, the serving dataset identity and the `moduleVersionKey` of the exact selections. A placement record's key is the canonical identity used to look up a report in `content.reports` or a summary in `content.courses`, and its value is the containing node key. A `null` removal record needs no hydration.

Before it builds a forest the pane checks that every programme report, every string-placed module report and every string-placed course summary exists, except a root the server reports in `versionSelectionRequiredIds`. It projects the selected complete input directly with `buildProgrammeForest` over the reports it holds and `resolveStructure` with the input's edits and content. An incomplete input falls back to the last complete input of the same dataset and selection identity, and with none the pane draws the empty forest. The last complete input is held in an effect and carries both identities, so a dataset or selection change never draws the previous forest, and a language change re-projects the held input in the live language.

The same selection key is part of the reconciliation key, and the reconciliation effect does nothing while any group needs a version. The gate always holds the server's required-root settlement, and adds the `versionSelectionRequiredIds` of the resolved projection while no Sisu capture is pending, so the pane draws every picker from those two facts alone.

The projection collects ambiguity only from selected, unsuppressed references, including notes: a defined placement that names another node excludes the whole reference subtree, an unchosen option contributes nothing, and a reset that clears a branch's choices drops that branch. A root the server settles as selection-required contributes its own requirement without placement filtering, and the drawer can offer unselected optional content as a note without requiring its version.

`useModuleVersionHandoff(onPick, inputRef, resetKey)` in `web/src/features/structure/useModuleVersionHandoff.ts` owns one lookup surface's ambiguous hand-off: the selected group, the Cancel control ref, direct single-candidate activation, the explicit pick, Cancel with focus in the surface's query field, and clearing when `resetKey` changes. `ModuleVersionHandoff` in the same folder renders the shared Cancel control and `ModuleVersionPicker` once for a non-null group with the surface's disabled value.

`ModuleLookupBox` passes `JSON.stringify([open, query])` with its query ref, and `DrawerSearch` passes `JSON.stringify([open, query, filter, node.key])` with its module callback and its own disabled value, so each surface keeps its query, category, target and close ownership. Every `LookupVirtualList` caller passes a module-scope key function, the version picker memoizes its candidate rows over the catalogue and the group, and the picker passes no query ref because it has no query field.

`web/src/features/structure/structure.css` owns the tab's layout. The rules that release the fixed title area, let a card take the height its content needs, and let tree, picker and drawer names wrap sit under `.structure-tree`, `.structure-root-overlay` and `.sdrawer` at widths up to 680 pixels. The same `CourseTile` renders a structure card and a graph course card. `tile.css` and the graph styles supply the graph geometry, and the structure scopes apply to the structure surfaces alone.

The same complete projection supplies `placedCourseIds` to the ordinary reconciliation. The effect captures the serialized programme list, choices and placements of the render, refuses while a Sisu capture is pending, and returns null when the stored structure does not match that snapshot, so the next store update renders the input current at that time. Action-time projections in the editor and the programme mutations stay where they are, because those validate the current state.

## Pane hooks, dialogs and programme operations

`web/src/features/structure/StructurePane.tsx` composes the tab:

- The pane reads the ordered programme identities, the choices, the two placement maps, the exact version map and `pendingSisuImport` from its profile selectors, and `usePlacedContent(courseIds, moduleIds, moduleVersions, allowUnrepresented)` is the one hydration owner. It receives every selected identity and every string course place, every programme identity and every string module place, so the programme reports and the placed modules and courses arrive through one effect under one selection identity.
- The pane builds the forest from the programme identities when those reports exist. While the hydrated content lacks a programme report, the report of a placed module, or the summary of a placed course, the pane holds the last complete programme list, edits and content, which re-projects that input in the live language instead of blanking the tree. It renders the hydration failure and the editor's failure as `ErrorNotice`, so a refused operation reads in the profile language.
- A reconciliation effect runs inside `applyStructure` with the current state. It returns `null` when the derived placed identities already equal the stored ones, and `null` as well when the hydrated content lacks a report the identity list needs, which leaves the hydration owner to load it.
- While `pendingSisuImport` is not null the pane reads with `allowUnrepresented`, runs no ordinary reconciliation, and holds the structure loading state, so no editing surface reaches the pre-resolution choice maps. The required version pickers render above that loading state, and the placement effect returns while the server settles a root group of the capture as needing a version selection or the profile holds saved edits.
- The picker gate adds the projection's nested requirements only while no capture waits, so a waiting capture is held by its own roots alone. The pane reads `sisuImportBlocked` from the profile as its own selector, so a restored profile that holds saved choices or places beside a waiting capture draws neither skeleton nor tree, hides the required pickers, and shows one `error-notice` status line with the shared wording. The resolver returns null for the same hold, so a render that has not caught up to a restored write places nothing.
- One effect captures the current profile identity, refreshes the saved envelope and returns when that identity moved, resolves the capture from the callback's own state inside `applyStructure`, and holds the returned issues in one transient notice. A failure renders its `ErrorNotice`, leaves the pending record in place and applies nothing.
- `SisuImportNotice({ issues, onDismiss })` renders the issues of one placement as an animated shell above the tree, each with its localized reason and its code or name, and it is visible until it is dismissed or unmounted.
- The Add row slot holds `AddProgrammeRow`, and while the ordered programme list is empty it also mounts `<ProfileTransfer store={store} importOnly />` inside `.structure-empty-import`, so the empty tab offers the same file picker, parse dispatch, script copy, import help and three confirmations as the profile menu without the export controls.
- `useProgrammeActions(content, extend, confirmMoves, contentDatasetIdentity, contentSelectionKey)` owns the Add and Replace operations. It captures the profile identity, the programme list and the content selection key, builds the prospective version map from the refreshed stored map plus its picked exact id, and reads through the shared `readProspectiveStructure` owner described below. It awaits the chosen reports, refreshes the saved envelope, refuses an incompatible list, profile or selection, and calls `changeProgrammes` with the prospective map and the whole placed content.
- `moves(operation)` reads a `ProgrammeMovePreview` through the operation's own report: the holder identity, the prospective version map, the pull list of the operation together with the node that displays its holder through `displayedPlace`, and Add asks for the move confirmation first when either exists and refreshes the captured profile and programme list again after the answer, so an Add whose list changed while it waited is refused before the write.
- `run(operation, removeCompletedCourses = false, pull = true, confirmedVersions?)` writes the `pull` mode its caller answered, and an Add whose own confirmation answered `keep` writes with `pull = false`. Reset and Delete use the loaded content through the same call.
- `useStructureEditor` owns the mutations. `commit(updateEdits, ctx, removed = [], nextProgrammes?, moduleVersions?)` derives the next edits from the current state inside `applyStructure`, resolves the current forest from the current programme list, and writes the supplied prospective version map or the current one without the entries of the groups the final projection does not render. It resolves the projection from the ordered programme list that `nextProgrammes` returns when the caller supplies it, so an operation that takes an identity out of that list writes the reduced list together with its edits, requires the target of a node-key action to be present in the current resolved forest, and raises `Structure target is unavailable` when it is not.

  `forgetRemovedModuleVersions(versions, before, after)` in `web/src/features/structure/moduleVersions.ts` is that one pruning helper: it collects the group identities of each tree's module nodes and drops only the entries of groups the before tree rendered and the after tree does not.

  `choose` writes the next choices through `nextChoices`. `addCourse` extends the placed content with the summary and places the course, and it reports `Already in this module`, or `Already in this programme` at a programme-worded destination, when the course already sits there. `selectRuleCourse` writes the options of the choice path and then the place. `toggleRuleCourseCompleted` places the course when it has no place and then toggles the completion, so the drawer completes an unselected course in its own rule without the **Mark completed?** question that the shared course menu and the graph ask. `deselectRuleCourse(course, removeCompletion)` takes the place away and names the identity in `removedCourseIds` only when the completion goes with it, and a loose completed course whose completion is kept returns without a change.

  `hasNodeEdits(node)` reads the open profile's structure from the store, derives the forest and answers `hasScopedEdits(forest, current, content, node.key)`, so the drawer asks before a removal whose current contents differ from the contents its own place draws with its own official defaults. `resetPulls(node)` reads the same stored structure and answers `scopePulls` for that node key, so the drawer can ask about the courses one reset returns before it writes.

  `resetNode(node, removeCompletedCourses = false, pull = true)` calls `resetUnplaced` for the bucket and writes a full change through `applyStructure` for any other node, so its scoped edits and its completion clearing both come from the same current profile state inside the callback. It writes the ordinary change for **Reset** and returns `resetCompletionChange` for **Reset all** in every state, so a scope that holds only completions and no change clears them, and its `pull` flag keeps the courses that `scopePulls` lists in the nodes that render them through `keepCoursePlacements`. It prunes the version map with `forgetRemovedModuleVersions` against the tree the callback resolved before the reset and the final projection, so a removed optional module loses its entry while the reset holder and every other rendered group keep theirs.

  Its notice reads `Programme reset to its official contents` or `Module reset to its official contents` from the wording kind of its target. `commit` is the owner of every other editor mutation.
- `modulePlacement(current, ctx, module, targetKey, item, pull = true)` is the pure preparation of one module operation. An official selection extends the choices along the item's choice path first, and a searched addition keeps them. The module identity's destination inside itself raises `A module cannot be added inside itself`, a target the candidate forest lacks raises `Structure target is unavailable`, and the result holds the placement edits, the pulled courses, the visible source node and `moveKey`.

  The tree the choice extension has not reached decides whether the tree renders the module before the operation: a module it does not render adopts its scope's official defaults while one it renders moves with its whole subtree, and its node of that tree supplies the source of the move. The source node is the node whose displayed children render the module identity, found through `displayContents`, and it counts as a module move when it is a programme, module or forest-wrapper node other than the destination, so a module held by **Unplaced studies** and a module the destination already renders move without a module sentence.

  Its destination resolution is read from the forest whose ordered programme list omits the module identity, so a module that list holds renders at the destination node and holds no entry at the programme level. Its source can therefore be the forest wrapper, whose node kind is `group`, for which `modulePlaceText` answers **the programme list** instead of `resolvedNodeLabel`.

  `pull` reaches the adoption, and `moveKey` is a transient serialization of the source node key, of the node key the module itself renders at, and of the pulled course identities with the node keys they leave, sorted by identity.
- `finishModulePlacement(module, targetKey, item, ctx, controller, profileId, programmes, operationDatasetIdentity, moduleVersions, baseSelectionKey)` confirms and applies one module operation on the current structure. It refreshes the saved envelope and returns without a write when the open profile differs from the captured identity. A different programme list raises `Structure programmes changed while adding a module`. A searched addition whose target already renders the module reports `Already in this module`, or `Already in this programme` at a programme-worded destination, and returns.

  It asks `confirmMoves` once when the preview has a module source or a nonempty pull list, reads the answer as the `pull` mode the write applies, honors the abort signal after the answer, refreshes the envelope again against the captured selection key, reads the hydration owner's current in-memory content through `extend({ datasetIdentity: operationDatasetIdentity, reports: ctx.reports, moduleVersions })`, and calls `commit` with that content, the prospective version map and a callback that verifies the programme list and recomputes the placement, together with a `nextProgrammes` factory that returns the captured ordered programme list without the module identity, so a module that list holds leaves it as that write lands.

  A recomputed `moveKey` other than the authorized one raises `Structure moves changed while confirming a module` before the write, so a change another tab saved while the question waited reaches the next structure and an incompatible one writes nothing. The added-module notice with its moved-course count follows a successful commit, and a kept course is not reported as moved.

  `addModule` reads the module report into the placed content and then delegates to it, and `selectRuleModule` delegates with its rule item and the owner key of that item, so both entry points share one placement, one confirmation and one write.
- `runModuleOperation(source, targetKey, item)` holds the lifecycle both module entry points share: it aborts the previous operation, captures the profile identity and the ordered programme list from the store, sets the pending module identity and clears the visible error, reads the placed content through the source preparation or uses the supplied content, and clears the pending identity in its cleanup. A failure reaches the editor error state unless the operation was aborted or the open profile changed.
- `ProgrammeMenu` renders the row menu. `ProgrammeConfirmDialog` renders the replacement-only named confirmation and retains the replacement, its name, the displayed place and the completion presence that the question opened with through the closing animation. [Replacing, resetting and deleting a programme](/docs/frontend/structure-editor.md#adding-replacing-and-deleting-a-programme) states the question, its actions and the outcome for the replaced programme. The dialog passes `true` to `onConfirm` from **Pull** and **Replace**, and `false` from **Keep**.

  `ModuleRemoveDialog` is the shared compact owner of a programme or module removal question and of the shared reset question. Its required `operation` prop of `remove` or `reset` selects the removal or the reset presentation, and its required `holderKind` prop of `programme` or `module` selects the nouns of the title and of the description. [Deselecting a course or a module](/docs/frontend/structure-editor.md#deselecting-a-course-or-a-module) and [Resetting a part](/docs/frontend/structure-editor.md#resetting-a-part) state the questions, their actions and their outcomes.

  The description is chosen from the operation, the holder nouns and the completion presence. It retains the name, the completion presence, the operation and the holder kind that the question opened with through the closing animation.

  `CourseMoveConfirmDialog` renders one `CourseMoveRequest` and answers through `CourseMoveAnswer`: `true` for the pulled courses moving in, `"keep"` for the operation applying with each listed course left where the tree shows it, and `false` for a cancelled operation that writes nothing. A request that carries a pull list resolves `true` and `"keep"`, and one without a list resolves `true` from its single move action. [The addition and move confirmations](/docs/frontend/structure-editor.md#shared-courses-and-the-later-addition) state the question, its actions and the place its `moduleFrom` formatter names.

  `AddProgrammeRow` renders the row that starts one.
- `StructureDrawer` renders the added-course section and the added-module section as one animated shell each with an `AnimatePresence` list, so a removed course or module animates out and the empty section collapses instead of vanishing, and a section stays mounted while its last row leaves. Both follow the shared transition, which changes at once under reduced motion. It keeps its displayed closing target in component state, clears it on the drawer's own transform transition end, and clears it directly when reduced motion is on.

  A module row whose current contents differ from the contents its own place draws with its own official defaults, or whose module holds completed courses, removes it through `ModuleRemoveDialog`. Its ordinary choice calls `deselectRuleModule` without removal identities, and its destructive choice passes the completed identities as the removal list. [Deselecting a course or a module](/docs/frontend/structure-editor.md#deselecting-a-course-or-a-module) states both outcomes. A row whose placement gives it its own official contents, the courses that placement pulled out of another holder included, and that holds no completion removes at once.

  The drawer's reset preserves the pending target and its opener, opens that same component at every press for a programme or module with `operation="reset"` and the wording kind of the pending target, and calls `resetNode` with `false` for the ordinary reset and `true` for the destructive reset. [Resetting a part](/docs/frontend/structure-editor.md#resetting-a-part) states the question, its actions and both outcomes. A reset whose `resetPulls` list is not empty asks a second time through the same `CourseMoveConfirmDialog`, and its answer decides the `pull` mode: `"keep"` and `true` run the reset with that mode, and `false` writes nothing. A scope that holds no completed course and returns a course asks through that pull question alone.

  The drawer's reset and removal completion presence reads the resolved subtree of the pending target against the live completion selector. `ConfirmDialog` from `web/src/shared/ConfirmDialog.tsx` appears when `courseHome` names another node, and the move runs at once when it does not, which covers a move out of **Unplaced studies**.

  `CompletedCourseDeselectDialog` appears for a completed course and receives the course code and the drawer's `unplaced` value, which selects between the two outcomes that [Deselecting a course or a module](/docs/frontend/structure-editor.md#deselecting-a-course-or-a-module) states. The drawer reads `editor` through a ref so a formatter created at click time uses the live `courseHome`. A rule row's module option and the drawer search's module result call `selectRuleModule` and `addModule`, whose own confirmation covers the module move and the courses an addition pulls, and the search closes on a selection.
- `useFreeChoiceAdd` binds the shared selected-set writer to the live store. It reads the count the current saved envelope gained, and `add` shows one notice whose text is the singular, plural or zero message and whose action is a **Structure of studies** link that opens the tab. Every course card and both add-all actions add to Unplaced studies through it.

`useNotice` in `web/src/shared/useNotice.ts` reads `NoticeContext`. `NoticeProvider` in `web/src/shared/NoticeProvider.tsx` owns one formatter-resolved notice, its optional action, its 2200 ms lifetime and the `ErrorNotice` of a failed action. `App` mounts it with the current profile as its key, so a profile switch clears the notice and the docs route unmounts it. No component holds a second notice state.

`PickerOverlay` renders its scrim beside the picker and wraps the picker alone in the optional `anchorClassName` wrapper. `StructurePane` renders `PickerOverlay` directly inside `.structure-root-overlay`, which spans the whole pane from its top edge, so the scrim covers every row of the tree, the pane's padding and the strip above the first row, and passes `.structure-root-anchor`, a sticky zero-height element inside the overlay's inline padding that is the picker's containing block, so the picker holds one place in the visible tab area whatever the scroll position of the pane. While a structure drawer is open the anchor narrows to the drawer-aware width and stays centered, so the picker follows the state of the drawer. A pointer press inside an open dialog and the Escape key of an open dialog belong to that dialog, so the **Add programme** picker stays open for the next pick.

## Request handling

`usePlacedContent` reads the missing summaries once through `readCachedCourseSummaries` and every missing module report once through `readCachedStudyStructures`, so the hydration owner never sends one request per identity. Its hydrated state carries the serving dataset identity and the exact selection key. A render whose state belongs to another identity or key shows an empty view and reads the missing inputs once under that identity and key, and the effect is keyed on the serialized identity lists, the mode, the exact selection map and that observed identity.

It drops a settled result whose controller was aborted and aborts the controller on cleanup, so a change to either list, a change of mode, a change of the selection map and an unmount cancel the pending read. It throws `Requested course summary is missing` when the read omits a requested identity in the ordinary mode and records that identity as unavailable in the pending mode. The structure response's `unavailable_root_group_ids` become unavailable modules in the pending mode alone, and its `version_selection_required` identities become the separate required-root settlements that the picker gate reads. Recorded identities count as settled for the request, so its `loading` finishes, and both settled lists clear when the selection key changes.

`extend({ datasetIdentity, courses?, reports?, moduleVersions? })` requires the extension's identity to equal the cache identity and reports to carry their prospective selection map, merges onto held content only when that content carries the same identity and selection key, merges the courses a supplied report already carries into the same content map, and installs the merged result as live hydration only for the live selection key. When a summary read and a structure read return different identities, the hook fails with one dataset-changed error and updates nothing.

`readProspectiveStructure({ cache, content, contentDatasetIdentity, contentSelectionKey, extend, state, groupId, moduleVersions, operationDatasetIdentity, signal })` in `web/src/features/structure/structureReads.ts` is the one prospective-read owner for the programme operations and the searched module addition. It derives the requested roots through `structureRootGroupIds`, reuses the supplied content only when its dataset identity, its selection identity and every requested root match, and otherwise reads the whole requested set once through `readCachedStudyStructures`. A read rejects cancellation through `cancellationError`, accepts the operation identity, refuses a missing or selection-required candidate with `Programme is unavailable`, and returns the extended content beside that candidate's report.

The caller keeps its stored-conflict check and its operation lifecycle, and returns without a write when the signal is aborted. `useProgrammeActions` and `useStructureEditor` also receive the dataset identity and the selection key of the supplied content, so a held report answers an operation only while both are current.

`addModule` merges the read report into the placed content, and `selectRuleModule` uses the report the open rule tree already carries. Both module operations refresh the saved envelope with `store.refreshFromStorage()`, return without a write when the refreshed current profile differs from the captured identity, throw `Structure programmes changed while adding a module` when the refreshed programme list differs from the captured one, and throw `Structure version selection changed while adding a module` when the refreshed version map differs from the captured selection key. The loaded branch of a module operation reports a changed serving dataset with `The serving dataset changed during the read` and a changed selection with the version-selection message, so the two failures stay distinct. A changed programme list never reaches a different forest.

The move confirmation waits between two such refreshes, the write recomputes the placement inside `applyStructure` from the current profile state, and a recomputed move identity other than the confirmed one throws `Structure moves changed while confirming a module` without a write. `modulePlacement` throws `A module cannot be added inside itself` when the destination sits inside the module.

`errorPresentation` maps these messages, and the projection and resolution messages, to `UI_TEXT` keys, so each failure reads in the profile language.

## Where a change belongs

- A drawer row or dialog to add belongs in `StructureDrawer` with its own component beside it, and an editor operation to add belongs in `useStructureEditor`. Every scoped mutation derives its next edits from the current state inside `applyStructure`, through `commit` or through the full change a reset builds, so no edit reaches a stale projection.
