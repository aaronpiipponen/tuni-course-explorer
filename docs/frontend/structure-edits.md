# Structure edits

The structure edits hold the profile's placement records, move a relocated scope's records, and write the structure slice together with the shared course sets.

## Placement edits, addition precedence and scoped reset

`web/src/features/structure/edits.ts` holds the pure placement edits.

- `place(edits, field, homes, id, target)` deletes the old entry of the identity, writes the target when it is not null, and writes a `null` target only when the identity has an official home. An identity with no official home is dropped instead. `placeCourse` and `placeModule` bind the course and module fields.
- `insideScope(scopeKey, key)` answers whether a key is the scope key itself or sits under it, and `resetScope` uses it to drop the choices whose key is inside the scope and the placements whose target is inside it. With `keepExternalPlacements` false, which a reset uses, it also drops a placement whose target is outside the scope when the identity's official home is inside it. A delete or replace passes true, so a course manually placed in another programme keeps that place.
- `officialPlacementTarget(root, edits, content, field, id, targetKey)` returns the exact official containing key one course or module move targets. It resolves a discovery projection with the moved identity's own placement set to `null`, so no earlier shared official occurrence consumes that identity and the target keeps its own entries. Only the target and the choice or transparent children that `displayContents` flattens are inspected. A direct match at the target wins, then the first matching flattened occurrence in displayed order. An unselected option and an official reference inside a different visible module do not qualify, and no match returns `targetKey` unchanged, which keeps the placement an addition.
- `moveScope(edits, content, from, to)` rewrites the records one moved scope owns for the node keys it renders at in its destination place.

  The two renderings come from the same official rule and the same placement records, so `scopeKeys` pairs their nodes and their choice options in the order the rule names them, pairs a module a record places inside the scope by identity, and reads each key from the projection on its own side, because a module's contents take their keys from the rule key of its own root rule rather than from a plain extension of its node key. A pair that does not line up raises `A moved scope does not match its new place`.

  A record under the moved node key that no paired node names holds a place the destination rendering does not have and leaves the state, a choice key and a placement target take their paired key, and a removal or a placement outside the moved node describes an identity and stays as it is.

  `replacedScopeHomes(homes, movedKey)` returns the official homes the clearing of a replaced scope reads, with the homes of every identity the moved subtree names removed, so the clearing keeps the removals and the places of the subtree that moves out of it while the replaced programme's own records clear with it.
- `hasScopedEdits(root, edits, content, scopeKey, courseOrder?)` resolves the forest with the stored edits and again with the candidate `holderPulls(root, edits, holderNode, content, false).edits`, which is the state a held identity shows when its own place draws it with its own official defaults, and compares the two targets as `scopeValue` tuples. The current target must resolve or the call raises `Structure target is unavailable`, and a candidate that does not render the target counts as a difference. A supplied `courseOrder` also compares every displayed holder's course sequence inside the scope, ordered by that list, with the candidate's unranked sequence, so a saved card order counts as an edit.

  A tuple holds the node key, the module identity, the rendered course identities, the notes the projection shows and its children tuples, so a record that leaves the rendered contents the same, such as an empty choice list, a chosen option that renders the same contents, or a place at an official home, is not a difference, and neither is a course the candidate pulls out of another holder into the scope. `Homes` is the exported map type the placement helpers share.
- `holderPulls(afterTree, afterEdits, holderNode, content, present, pull = true)` returns the next edits of one added holder, the courses and the modules that move with them. The holder node is resolved on its own rule with no choices and no content, so each record is the holder's own first place for a module or a course it officially renders and only its default contents are read: an option the profile does not select by default contributes nothing. The module records name the node whose entries render the module. Each listed move's `from` formatter reads `courseSource` or `moduleSource` on the tree resolved from `afterTree` and `afterEdits` before the holder's scope records are cleared, so a row a chosen option draws names its containing programme or module rather than the choice title.

  A module of the holder's own rule that the tree renders outside the holder is listed once, at its highest official level, and the whole current subtree it holds travels with it, so no course or module inside it is read or listed again. A module that renders inside the holder or nowhere is searched further, which can list a nested module that the tree renders elsewhere. A listed module that the ordered programme list renders is named with **the programme list** as its place, and a pulling write removes it from that list and moves its records into its own official place inside the holder.

  The `present` flag is whether the tree renders the holder before the operation's own writes, which means the operation moves the holder. A moved holder returns `afterEdits` and an empty move list, so the whole current subtree it holds travels untouched: a removed identity stays removed, a course it renders elsewhere inside its own scope or directly in the `u` bucket keeps that place, an official course another programme or module renders stays there, and no module takes its official place again. A holder the tree does not render adopts its scope's official defaults, because the records `clearScope` drops from that scope are removed before the restoration, and a module the cleared projection renders nowhere takes its official place again, which brings the courses inside it with it.

  A place or a removal outside the holder stays as it is, because the clearing touches only records whose key or target is inside the holder, so the holder restores only the official identities that render nowhere. The courses are read against a projection that includes those restored module records, and a course the cleared projection does not render at its own node takes the place of that node again.

  The move list reads the tree before the scope's records are cleared, so a course of the holder's own rule that the tree renders outside the holder is listed as a move from the node the tree shows there and takes the holder's own place, while a course that renders nowhere or that renders directly in the `u` bucket is not listed and keeps its place.

  `pull` is whether the listed courses and modules move in: a kept course keeps the record it holds and no place is written for it, so the node outside the scope keeps rendering it and the adopted official contents render without it. A kept module stays in the node that renders it now with everything it holds, while a pulled module moves through `placeModuleWithCourses` into its own official place and keeps its current subtree.
- `scopeModulePulls(root, edits, content, scope)` returns the highest-level official modules of one scope that the tree renders outside it, with the node that renders each one now, the module identities the ordered programme list renders, the official keys of the listed modules and the containers that render them. `pullModules(root, edits, content, scope, modules, programmeIds)` moves each listed module into its own official place inside the scope, through the ordered list for a module that list renders and through `placeModuleWithCourses` for every other one, so a pulled module keeps its whole current subtree.
- `placeOfficialCourses(root, edits, content, scope, ids?)` returns edits that render the scope's official courses at their own official places. A course with more than one official home can be drawn at another home once a reset clears its record, so the reset scope pins each course it restores, and `ids` limits the write to the courses a caller keeps.
- `officialPulls(root, edits, content, scope)` returns the scope's own default courses and highest-level modules that the tree renders outside it, with the place each one sits in now and the module containers. A module is listed once and nothing inside it is read again. A course counts even when another official home currently wins the precedence, so the reset prompt names every official identity that the tree renders outside the scope.
- `restoreScopeContents(root, edits, content, scope, pull)` returns the edits one scope's restoration writes and the `officialPulls` it read. It clears the scope's records, moves the listed modules into that scope on `pull` and pins the scope's official places, or keeps the listed courses and modules where they are through `keepCoursePlacements` and `keepModulePlacements` and pins the official courses the scope renders now. Only the identities the scope's restored content renders have their records cleared, so an official home that a placement or an option the reset clears supplies leaves the record of the node that renders the identity now alone. The drawer reset, the programme reset and `resetMoved` apply their own later steps over its result.
- `resetMoved(root, edits, content, destination, mode, pull)` returns the edits of a moved module reset at its new place. It applies `restoreScopeContents` at the destination, keeps that result's edits, and returns the pulled programme-level identities with the edits. A kept-completion reset places every dropped course in Unplaced studies and a destructive reset leaves none there.
- `keepModulePlacements(edits, previous, pulls, containers, shared)` returns edits with the placement record of each listed module as the previous edits hold it, so a kept module stays in the node that renders it. A module the ordered programme list renders is not written, because that list keeps it.
- `keepCoursePlacements(edits, previous, pulls)` returns edits with the placement record of each listed course as the previous edits hold it, and with no record for a course that holds none. A scope clear drops the record of a course whose official home is inside the cleared scope, which is what returns that course to the scope, so this is the owner that keeps such a course where it is: `holderPulls` reads it for a kept addition, and the reset owners read it for a kept reset.
- `placeModuleWithCourses(root, edits, content, moduleId, targetKey, from?, pull = true, reset?)` normalizes the displayed destination through `officialPlacementTarget`, places the module there, resolves the tree to find the destination node of that module, and returns `holderPulls` for that destination together with the next edits. The normalized key makes the official branch authoritative when the target officially names the module, and its display holder key is unchanged for order and disclosure metadata. Its `from` node is the pre-operation rendering of the module in the caller's own tree, which `modulePlacement` reads from the tree the choice extension has not reached, an omitted node reads the module of the supplied edits, and a rendered module moves with its subtree through `moveScope` before the placement resolves.

  The courses and modules a module it does not render pulls belong to the caller's confirmation, `pull` decides whether that placement moves them in, and a moved module pulls none. A moved module that the caller resets clears its own records at the destination, and a kept-completion reset places every course the reset drops out of the tree in Unplaced studies while a destructive reset leaves none there.
- `clearedScopePlacements(affected, afterTree, afterEdits, content, touched, completedCourseIds)` returns the records that keep a cleared scope's courses out of the nodes the action does not touch. A course that the cleared scope rendered, and that the next projection renders in a node outside `touched`, is placed in `u` when it is completed and removed from the tree when it is not. How the scope held the course makes no difference, so a course that rests on its official place alone counts the same as one an explicit placement holds.

## Selection migration and the shared sets

`web/src/features/structure/actions.ts` holds the only writer that moves the structure slice and the shared course sets together.

`applyStructure(store, change)` runs the callback inside `store.updateCurrent` with the current profile state. A callback that returns `null` leaves the state as it is and writes nothing. Otherwise the returned `next` structure and its explicit identities migrate the shared sets:

1. A course named by `state.structure.placedCourseIds` that the next projection does not hold, and that is not completed, is dropped from the selection.
2. An identity of `discardUncompletedCourseIds` that is not completed is dropped as well.
3. An identity of `removedCourseIds` leaves both course sets, so the removal of a completed course takes its completion with it.
4. The selection that is left keeps its order, and every identity of `next.placedCourseIds` that is absent is appended.
5. The structure slice is written as the next programme list, the exact version selections, the choices, the course placements, the module placements, the placed identities, the course holders and the card order.
6. The card order keeps only identities that the migrated selection holds, so a course that leaves every set leaves the order in the same write.
7. `pendingSisuImport` is written from the change when the change supplies it and kept as it is when the change omits the field, so one write places a pending capture and clears it together.

A completed course is never dropped by steps 1 and 2, which is what keeps a completion across a programme replacement, a reset, and a module deselection. An explicit removal is the operation that drops it.

`programmeOutcome(state, operation, content, completedCourseIds, pull, reset?)` is the one owner of the programme operations. It computes the next programme list, the scoped edits, the card order, the pulled courses and the uncompleted discards of one `ProgrammeOperation`:

- `{ kind: "add", groupId, versionId }` refuses a programme the list already holds with `Programme is already added`, appends the identity, and adopts the appended programme's official defaults while it records the courses and modules that programme pulls. The picked exact id joins the prospective version map, and an entry that disagrees with the stored map refuses the write. A programme another node of the tree displays moves to the list with its whole current subtree, which `moveScope` rewrites for the top-level key. The addition drops that programme's own placement record before the after tree resolves, because the ordered list renders the identity and a record, a removal record included, would suppress its entry.

  A moved module that the caller resets clears its own records at the promoted place, and the destructive reset clears the completions the moved subtree held. The outcome also reads the reset actions its confirmation offers from `moveResetOptions`, which combines whether the moved scope holds a structural edit with whether it holds a completed course.
- `{ kind: "replace", groupId, replacementGroupId, versionId }` keeps the affected position, refuses an identity that another top-level position holds, reads the replacement node of the state that starts the operation, clears only the records the replaced scope owns, and records the courses and modules the replacement pulls. The picked exact id joins the prospective version map under the same conflict rule. A delete or replace keeps a course manually placed in another programme, and the replacement's pull confirmation offers **Keep** and **Pull** for its own official courses rendered elsewhere.

  A replacement programme that the tree already displays keeps its own subtree: `moveScope` rewrites its records for the top-level key and the clearing reads the official homes without the keys of the moved node, so the moved choices, additions and removals survive while the replaced programme's own records clear around them, and the replacement's own placement record is dropped before the after tree resolves, because the ordered list renders the identity and a record, a removal record included, would suppress its entry.

  A replacement the tree does not display adopts its official defaults, and its clearing and its adoption both read the edits that already dropped that record, so a removal record of that identity does not suppress its top-level entry.
- `{ kind: "reset", groupId }` restores the scope through `restoreScopeContents`, which lists the courses and modules through `officialPulls`, moves the modules through `pullModules` and pins the scope's official courses through `placeOfficialCourses` on `pull`, and restores their records through `keepCoursePlacements` and `keepModulePlacements` on a kept reset. A course the restored content will not render stays where the tree renders it, even when its official home was inside the scope through a placement or an option the reset clears, and a course under Unplaced studies returns to the scope without being listed. On `pull` it then drops the pulled programme identities.
- `{ kind: "delete", groupId }` removes the identity and clears the same scope, and it works for the last programme.
- The card order of a reset clears the ranks of the courses the affected subtree held before the write and of the courses the final projection places inside that scope. A delete clears the departing programme's held ranks. A replacement clears them except for the courses of a replacement subtree that the tree already displays and moves intact. An addition keeps every rank, so a promoted programme or module keeps its courses' relative order. `clearCourseOrder(order, ids)` performs the one removal.
- A missing programme or a report the content lacks raises `Programme is unavailable`, and no branch fetches, falls back or writes.

`changeProgrammes(store, operation, content, removeCompletedCourses = false, pull = true, moduleVersions?, reset?)` runs that outcome inside `applyStructure` and writes the full next structure with the uncompleted discards of the affected programme. Its trailing `moduleVersions` is the prospective selection the operation's reports were read under, it defaults to the stored map, and an entry that disagrees with the stored map raises `Another version of this module is already selected` without a write. Its `removeCompletedCourses` flag is the destructive choice of the entry point that offers one.

For a delete it is **Delete all**: the affected programme's completed courses join `removedCourseIds`, which takes them out of both course sets, and a `null` placement takes them out of the tree so no surviving programme brings them back. For a reset it is **Reset all**, which passes the prepared ordinary change to `resetCompletionChange`. An ordinary reset and every delete without the flag write the ordinary change.

Its `reset` argument carries the reset mode `keep` or `all` that a module move chooses into an addition or a replacement. An addition or a replacement that moves a holder and carries `all` passes the moved scope's own node key and the promoted node key to `resetCompletionChange`, so the completions the moved scope held before the write are cleared while the promoted scope keeps its restored places.

Its `pull` flag is whether the addition, the replacement and the reset move the listed courses in, whether the addition and the replacement also move their listed modules, and a kept reset keeps its listed records through `keepCoursePlacements`. The write resolves the current forest from the callback's current stored structure and passes it with the final projection to `forgetRemovedModuleVersions`, so the departing programme and every nested module it rendered lose their version entries while retained groups keep theirs.

`resetCompletionChange(state, scopeKey, content, ordinary, restoredKey = scopeKey)` adds the destructive reset outcome to one prepared ordinary reset change. It resolves the pre-reset forest from the callback's state and requires the target node, raises `Programme is unavailable` or `Structure target is unavailable` when either is absent, and reads `removedCompleted` as the intersection of that node's subtree identities with `state.completedCourseIds`, so only a completion the scope actually holds is cleared. `restoredKey` names the scope the ordinary change renders, which a moved module reads as its destination while the held identities come from the scope it leaves.

It copies the ordinary change's course placements and leaves its choices, module placements and programme list as they are. A restored placement is kept when the candidate projection locates that identity inside `scopeKey`, and set to `null` otherwise, so a discarded completion cannot fall back into an untouched holder and a restored mandatory course is selected.

It returns the ordinary change with the final placement map, the final placed identities, the ordinary card order, and `removedCourseIds` equal to `removedCompleted`, and it preserves the ordinary change's uncompleted discards and pending-import field. `applyStructure` removes `removedCourseIds` from both course sets before it appends the placed identities, which is the order that selects a restored mandatory course as uncompleted.

`programmeMoves(state, operation, content)` returns the listed courses and modules of the same outcome, the reset lists of a promoted module, and the reset actions that module's own state allows, so an interface confirms them before the write and a cancelled confirmation writes nothing. It answers a reset with the courses that reset returns to its scope through `officialPulls`. `displayedPlace(state, content, groupId)` returns the localized node that displays one identity of that state, and a direct `u` bucket entry answers with no node because that bucket holds unplaced items by definition.

`resetUnplaced(store, content)` resolves the forest, collects the courses of the `u` subtree and the selected courses outside the whole forest, drops the `u` choices, keeps a placement whose target is outside the bucket, turns a placement into the bucket into `null` when the identity has an official home outside it, clears those courses' card ranks, and commits the resulting projection with the collected identities as uncompleted discards.

## Where a change belongs

- A change to how a place is stored, cleared, or discarded belongs in `edits.ts` and in `applyStructure` in `actions.ts`.
- A change to a programme operation belongs in `programmeOutcome` in `actions.ts`, which the write and the move list share.
