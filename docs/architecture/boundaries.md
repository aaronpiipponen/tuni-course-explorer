# System boundaries

course-explorer separates the course-exploration request path, the browser-held user state, official data, the preparation work, and the administration surface, and each separation is enforced in code.

The administration side runs the preparation work and fills the Working dataset, and the read-only side serves requests from the Selected dataset. The two paths meet at three shared artifacts. The PostgreSQL database with pgvector holds both role databases: the stages write Working, and the web server reads Selected. The separate feedback application store holds anonymous feedback submissions that the web server writes through the feedback service. The usage file under `data/usage/requests` is the third: the front router appends one request record per request, and the administration command's usage report reads and prunes it. The catalogue reads of the web server write nothing to the Selected dataset. The web server runs one front router and its worker processes, and the router holds transient admission counters and a transient feedback allowance in its own process memory, which no administration surface reads.

A separate feedback application store holds anonymous feedback submissions. `src/course_explorer/feedback/` validates each submission against the feedback definition in `config/feedback-form.json`, writes its validated images beneath `FEEDBACK_ATTACHMENTS_ROOT`, and stores the answers, attachment metadata, explicit publication choice and current publication outcome in the database that `config/feedback.toml` names. That database has its own metadata, migration chain and head, and no feedback row references a curriculum row or a dataset pointer.

A separate sender process holds the only GitHub credential, publishes at most one opted-in submission per activation through one bounded attempt, and records the created link or a safe failure in the feedback application store. The two public feedback paths are `GET /api/feedback/definition` and `POST /api/feedback`: the read reports the current feedback definition and non-secret destination metadata, and the write reaches the service through one bounded front-router admission. The serving path's own writes are the usage record and the transient admission and feedback state, and an admitted submission writes only this separate feedback application store.

The feedback owner answers the operator's fixed commands alone: a listing with configured search and filters, one attachment read keyed by both stored identities, and the deletion of one named submission. The listing reports the recorded publication outcome and issue link from the feedback application store, and it reads no GitHub issue state. The sender holds the only GitHub credential, and the serving processes receive no sender value. The three operator HTTP routes under `/api/feedback/` run those commands behind the administration backend's lock, exact-site, session and CSRF boundary. No anonymous route reads a submission or a file. The attachment bytes are a transient command carrier, and no path or retained byte copy leaves the owner.

A deletion removes the named submission's row, metadata and owned files and reaches no GitHub issue or GitHub-hosted image. [Administration commands](/docs/backend/interfaces/administration-commands.md#the-feedback-application-store-commands) states the commands and their visible failures.

## A read-only catalogue web server

No route of `src/course_explorer_web/` writes authoritative data, starts or controls a stage, or reaches the worker. The route set is fixed: eight dataset command reads and one feature read under `/api/`, the feedback definition read and submission write, three shell documents for the browser app, and one mounted asset directory. The feature read reports the site's two serving switches and the serving dataset identity, and it runs no command. The feedback definition read reports the current feedback definition and non-secret destination metadata, and the submission write reaches the feedback service after the front router's site, size and hourly checks.

The package imports no administration module, no translation module, and no ingestion or embedding command module. The front router appends one request record per request to the site's own usage file and holds the admission counters, tickets, graph costs and feedback allowance in its process memory. The usage record and that transient state are the serving path's own writes, and only an admitted feedback submission reaches the separate feedback application store. The counters and the allowance hold no catalogue or user data.

The launcher passes only named settings into the server process: the seven settings families every site needs, the embedding family on a site that serves embedding features, the inherited `HOME`, `PATH`, and `LANG`, `PYTHONPATH` with the `src` directory that holds the loaded package, the arena cap from `WEB_MALLOC_ARENA_MAX`, and the environment-only marker. The sender families, including `FEEDBACK_GITHUB_TOKEN` and `FEEDBACK_GITHUB_TIMEOUT_SECONDS`, are outside that handoff. A child built that way reads no settings file, so no other value reaches it. A feedback request reads `config/feedback-form.json` through the feedback service, because the feedback definition is not a settings source. The `course_explorer_web` tests assert the exact route set, the forbidden imports, the setting allowlist, and one recorded usage line per HTTP outcome.

The minimum route is calculated in the browser from the graph report, and the machine route command runs the same TypeScript solver through Node outside this package. Neither the route calculation nor its result reaches a server route, so the serving process holds no fallback solver. The narrowing boxes filter one cached minimal official catalogue in the browser. The catalogue route serves that minimal official catalogue: canonical identity, code, FI and EN names, credits and the activity flag for each course, and for each module group that has an eligible version, every version eligible for the current academic year with its `sisu_module_id`, `module_type`, code, FI and EN names, `validity_start`, `validity_end` and curriculum periods. The filter applies the official matching and ordering in the browser without another server request.

The reason is that the request path serves readers only. Model credentials, stage control, and the worker connection belong to the administration command.

## Feature switches

Two validated keys in `config/web.toml` decide which features a site's reads serve: `WEB_EMBEDDINGS_ENABLED` governs semantic matching, the Compare feature and the Recommended list of Discover, and `WEB_INFERENCE_ENABLED` governs every read and every mark of inferred data. Both are required and have no default, so each site states them.

The embedding switch also decides the serving artifact build and the supervisor startup. With it on the build writes the embedding artifacts and the supervisor opens them, and with it off the build writes the catalogue artifact and the study fragments alone. A site whose family holds none for the running configuration runs `scripts/admin.py serving-artifacts` before its supervisor starts. [Serving artifact build](/docs/backend/text-and-vectors/serving-artifact-build.md#the-embedding-switch) states each mode's files, tables and open.

The serving backend enforces them. A disabled embedding feature refuses the comparison and recommendation reads with status 403 before their command runs, and a search on such a site composes no semantic method, no embedding provider and no stored-vector read. A disabled inference feature is applied to the request input that toggles inferred data, so those reads compile official prerequisites alone. The browser hides the controls the site does not serve, and the stored data and the saved browser preferences are the same either way.

## Request usage records

The front router appends one request record per request to the ignored `data/usage/requests` of its own checkout, through one pure ASGI middleware around its forwarding handler. One record holds the hour, the route, the status and the duration, and no IP address, query, user agent or course data. A route label is one of the nine fixed API paths, one of the two feedback API paths, one of the three shell paths, `/assets` for the mounted asset directory, or `unmatched`, so a requested path, asset name or query is never retained.

A fixed command under `scripts/admin.py` reports the request count and the mean, p95 and p99 durations by window and route and prunes the records past the configured retention, outside the request path. That read and the serving append take one exclusive lock on the same file, so a record that arrives while a report rewrites the file is preserved. The request record is the only durable record the serving path's own request accounting adds, beside an admitted feedback submission in the separate feedback application store. The admission counters live in the front router's process memory, and no administration surface reads them. The Administration backend writes the command log in its own file under `data/admin-web/`, and [Console access and records](/docs/operations/admin-console/access-and-records.md) states both records.

## The administration surface

A deployment runs a separate administration surface: an Administration console, an Administration backend with its own package `src/course_explorer_admin_web/`, and its own configuration and serving process. The backend reaches the system through the fixed `scripts/admin.py` commands alone, with validated parameters and no shell or free-form command text. It therefore holds no direct connection to the database, no second controller over the stages and no service path of its own. It binds loopback alone.

The Administration backend authenticates its own operator. Each site holds one account with a username and an argon2id password hash, and one fixed command sets the password. Sessions live in the backend process's memory and expire at a configured idle lifetime and a configured total lifetime. The session cookie is HttpOnly, Secure, SameSite=Strict and scoped to its site. Every request must carry exactly one Host header equal to the configured origin's host and port, and every state-changing request needs a valid CSRF token and an exact Origin match.

The backend owns that boundary. One process binds the configured loopback address, serves the three authentication routes under `/auth/`, and serves the built console from `/` and from one mounted `/assets` directory. One admission middleware applies the lock, the exact Host and Origin check, and the CSRF token of a state-changing method before any route runs, so an unknown address and a mounted file are covered like a route. [Administration backend](/docs/backend/interfaces/admin-backend.md) names the middleware and its admission order.

The built shell and its built assets are the one read-only exception to the session requirement: a `GET` or `HEAD` of exactly `/` or of a path beneath `/assets/` is admitted before its cookie is read, and that request runs no command and records nothing. Every other address needs an authenticated live session, apart from `GET /auth/session`, which reuses its session or creates an anonymous one within the [anonymous session creation limit](/docs/operations/admin-console/access-and-records.md#the-anonymous-session-creation-limit), and `POST /auth/login`, which needs a live session of any kind.

Every feature route runs fixed commands of one closed command union. A single-command route runs exactly one of them. The route of the administration rebuild runs two: its build command answers the request, and only its successful response attaches the separate restart command as a background task that the framework runs after the final response body send. Sessions live in that process's memory, so a restart ends them, which is the sign-out that the administration rebuild causes. The failed-attempt count, the lock and the command log are files under `data/admin-web/`.

The [Console access and records](/docs/operations/admin-console/access-and-records.md) page states the admission order, the session rules, the lock and both records.

The console's frontend is a separate React application with its own build and its own manifest, built from `admin-web/` into `admin-web/dist`, so the course-exploration server can serve no admin file and the console holds no course-exploration asset. [Administration console code](/docs/frontend/admin-console.md) describes the build.

Three consecutive failed sign-ins create the Administration lock `data/admin-web/lock`. While that file exists, every request to that site is refused with a bare `403` and an empty body, before sign-in, any route and any static file, authenticated or not. The file lives on disk, so a restart and a reboot do not clear it, and only deleting the whole file ends the lock.

The enforced assertions on this page belong to two packages. The course-exploration web package refuses both administration packages by import, and its tests cover the route set, the setting allowlist and one usage record per request, with the usage report covered by the report's own tests. The Administration backend's tests cover its admission, its fixed commands, its routes and its command-log read. [Invariants and their enforcement](/docs/architecture/invariants.md) names the module that owns each rule and the tests that cover it, and [Administration backend](/docs/backend/interfaces/admin-backend.md) names the package and its test files. [System context](/docs/architecture/system-context.md) places the administration surface among the parts, [Administration console code](/docs/frontend/admin-console.md) describes the separate build, and [Operations](/docs/operations/README.md) states the operator's access and the record contract.

## User state in the browser

The selected and completed courses, the exclusions, the structure edits, and the app language live in profiles in the browser's local storage. They reach the server only as request inputs, and a route that needs courses accepts the canonical identities and the toggles the browser sends. The server stores no profile and returns none, so the profiles belong to the browser that holds them. The open tab lives in the browser tab's own session storage and reaches no server either.

## Official and inferred data apart

Official data is what the ingestion stage writes from the public curriculum source. Inferred prerequisites and equivalence groups are stored in their own tables with their own coverage state, and the inference stage writes inferred output without modifying an official row. University facts and derived claims never share a store, so the interface can mark each derived claim as such. The app shows inferred prerequisites only behind the **Inferred** toggle, on a site that serves inference features, and marks each one **inferred**.

A translation is stored beside the text it was made from and does not replace it. Official text takes precedence, and a stale translation is reported and never used. [Data model](/docs/backend/catalogue/data-model.md) describes the stores, and [Inference](/docs/backend/inference/inference.md) describes what the inference stage reads and writes.

## Inference on local models

The inference stage runs language models on the worker, and the web server holds no model or worker credential. The inference subsystem file pins each artifact by revision and SHA-256 and names the loopback address and port the provider posts to.

Fit decides which local model receives a target. A target call starts only when its prompt tokens plus the configured output cap and headroom fit inside the context of one configured local key. A packet that fits no configured key is never shortened. It fails that target as one capacity failure, and the whole packet is either sent or reported as failed. The key list, the output cap, and the headroom are described in [Inference scheduling and disposition](/docs/backend/inference/inference-scheduling.md).

The web server receives none of these settings. Its launcher composes the database, normalization, search, web, admission, feedback application and feedback intake families, and adds the embedding family only on a site that serves embedding features, so no inference value, no sender credential and no worker connection value can reach the serving process.

## Configuration ownership

The subsystem files hold every non-secret setting, including machine and site identity such as the worker host, user and path and the systemd unit names. The environment file holds credentials only: the curriculum database password and the feedback application store's database password, the feedback sender's GitHub token and any provider credential a site uses. A site's external app address is one non-secret `WEB_APP_URL` in `config/web.toml`, and both the administration App link and the feedback exact-site boundary read it. Tracked templates live under `examples/config/` and `examples/.env.example`. The runtime copies under `config/` and the environment file at the repository root are ignored by Git, and an operator copies and customizes the examples through the same settings owner. Each value is validated before the process that reads it starts work, and a missing or malformed value fails the read. [Configuration](/docs/backend/configuration.md) lists the files and the keys.

## One current schema and format

Every process reads the database schema, the file formats, and the state files of the running code, and a mismatch fails before work starts. A database that is not at the single head of its owning migration chain is refused with fixed guidance, and a state file whose contents do not match its closed schema is refused rather than interpreted. The inference result contract accepts only the `v2` schema version. The browser reads only its schema-3 envelope and `/3` profile and state files, and the separate Sisu `/1` capture. A stored value or file of another shape fails validation and is left as it is. The recovery screen exports the stored envelope text exactly as stored or resets browser storage after confirmation, and an import file of another type or shape is refused at the file input and never reaches recovery. A stored prerequisite expression outside the current node vocabulary fails the read.

Data and code move together through explicit setup and migration, so a read is answered against the schema and the formats of the running code alone.
