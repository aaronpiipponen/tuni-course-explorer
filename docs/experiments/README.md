# Experiments

The Experiments section records the project's experiments, from the question each line asked to how it ran, what it measured, and where it ended.

## What a report records

Each report accounts for a line of related experiments. It gives the question the line asked, the setup and conditions of its measurements, and the values those measurements recorded, with the cohort, the ground truth or proxy and the timing boundary each value needs. A short label near the top of a report states the kind of evidence behind its main result.

A report keeps observation, interpretation and open questions apart. An observed result is what a measurement returned, and a negative result is recorded as one. An interpretation is what the report reads in that result. An untested question is one the line did not measure, and each category overview collects the untested questions of its line. A failed hypothesis and a design that was measured and then dropped are named as such.

Corrections stay beside the result they changed. When a later measurement corrected or reversed an earlier claim, the report states the earlier claim, the correction and the result that stands, so a replaced value is not read as the standing result.

Methods sit at the level they apply to. A method shared by one category, such as the reference answers and the blind judge in inference or the load setup in serving, is described on that category's overview or on a method page of that category. A method used by one report is described in that report. The [glossary](/docs/reference/glossary.md) defines the product terms the reports use.

## Evidence status

Each report carries one of five labels in a short line near the top. The label describes the evidence, not the quality of the page or the weight of the result. A report that holds more than one kind of evidence carries the label that qualifies its main result.

| Label | What the evidence is |
|---|---|
| Exploratory | The first measurements of a question, which set its cohorts and parameters rather than settle a comparison. |
| Comparative | Two or more variants measured on the same inputs, where the difference between them carries the claim. |
| Observational | A read of a running system or a profile of its behavior, with no variant measured against it. |
| Corrected | A line whose main result a measurement corrected or reversed, reported with the result that stands. |
| Reproduced | A measurement taken a second time on a separate run or implementation and matched to the first within a stated tolerance. |

## The catalogue the experiments read

The numeric experiments ran on a captured snapshot of the Tampere University curriculum from the public curriculum source, never on the invented example dataset. An installation of the app loads that example dataset, and its courses, modules, prerequisites and structure rules are not university data. The capture is configured for the academic years 2006-2007 to 2026-2027, with a three-year activity window set by `ACTIVE_ACADEMIC_YEAR_WINDOW`. The catalogue holds teaching text in Finnish and English.

The counts below describe one analysis snapshot of the catalogue, the course, module and chunk rows that one capture and normalization produced. It holds 11,086 courses, each counted once through a representative version, of which 4,543 are active. The same snapshot holds 9,901 eligible module versions and 58,962 teaching-text chunks, each with a BGE-M3 vector. These counts describe that snapshot, not every dataset revision or capture run.

A capture count and a normalized catalogue count measure different things. A capture stores course and module objects, and normalization reconciles them into the course versions a catalogue read counts. One full-catalogue capture recorded 24,932 course objects, which a source-free replay reconciled as 24,931 normalized course versions, with one explicit null-code exclusion and 88 unresolved course groups. A timed capture of the 2026-2027 academic year completed in 125.49 seconds, stored 6,071 responses and recorded 17,020 course snapshots and 3,724 module snapshots.

## The hardware

Inference and prompt work ran on an AMD Radeon RX 9070 XT (16 GB model) on ROCm 7.2.1, in a machine with 33.4 GB of usable RAM, and the translation-model work ran on the same card model. The translation-model record names ROCm but gives no ROCm version and no machine RAM value. Search, translation scoring, recommendation, graph, memory and serving-load work ran on a 4-core aarch64 server with 23.6 GB of RAM. These specifications describe the experiments that recorded them. The capture records do not state their hardware, so the catalogue's own capture cost has no machine specification in the section.

The reports do not share one build, one dataset revision, one payload set or one warm-up. Each report states the build, input set, model versions, settings and timing boundary its numbers need, including whether a run was warm or cold. A value from one line does not carry to another, and the section does not combine its results into one score.

## The five categories

The section covers five categories of experiments. Each category holds one line of related reports on one part of the system. Each subsection links its category overview, which carries the full accounts and the category's own untested questions.

### Inference

The [inference](/docs/backend/inference/inference.md) experiments asked whether one local language model on an AMD Radeon RX 9070 XT (16 GB model) could propose direct prerequisites and equivalence groups for every active course from teaching text alone. The line separated fit and throughput, candidate retrieval, the packet the model sees, the reference and judging method, confidence, prompt and schema tuning, held-out quality and the full-catalogue run.

The held-out benchmark on 2026-09-28 reported Qwen3.8-27B IQ3-MIX as the leading candidate at prompt version 9 and result schema version 2. The model and policy were selected on 2026-09-29. On 150 targets MIX returned 150 valid results, and the blind judge marked 111 of its 178 emitted findings supported. That count includes 54 of 100 required findings, 38 of 47 recommended findings and 19 of 31 equivalence groups, and 15 of the required findings were unsupported. The selection kept the model solo, with no confidence cutoff, no finding filter, no drop and no demotion, and with recommended options kept. Both the selected model and the ByteShape candidate measured about 60.5 seconds per complete validated held-out target, with no fit skip on the 150. The quality of that configuration was judged on the held-out benchmark before the full run, not on the published catalogue output.

The full-catalogue run then published all 4,543 eligible active targets in one completed cycle, with no failed target and no operator disposition. Of those sets, 2,348 carry a prerequisite expression and 2,195 are empty. The local route served 4,520 targets, and the run's explicit oversize route sent 23 oversize targets whole to DeepSeek V4.1 Flash. The run observed 227,150 of the expected 227,150 packet candidates, 50 per target.

The run does not validate the 4,543 outputs. The empty share cannot separate a correct empty answer from a model omission, and judged support, the share of emitted findings that a judge marks supported, is not the university's official record. A true prerequisite the model never emitted is invisible to judged support. The [Inference experiments](/docs/experiments/inference/README.md) overview carries the retrieval, packet, confidence, prompt and recovery accounts. The [reference answers and judging](/docs/experiments/inference/reference-answers-and-judging.md) page states the shared method, and the [held-out model quality](/docs/experiments/inference/held-out-model-quality.md) and [full-catalogue inference run](/docs/experiments/inference/full-catalogue-inference-run.md) reports hold the two results above.

### Search and translation

The [search](/docs/backend/search-and-discovery/search.md) and translation experiments asked two separate questions. The translation line asked whether a machine translation can stand in for official text without breaking retrieval. The search lines asked whether an exact semantic read can be cheaper without changing its set or order, what a bounded approximate index loses, and whether SQL can reproduce the Python lexical set and order.

TranslateGemma 12B at Q5_K_M translated 60 cases in six cells, with 10 cases in each cell. The generated text retrieved its paired official counterpart first in 59 of 60 cases, a rate of 0.9833, with a mean reciprocal rank of 0.9875, and every cell stayed at or above 0.80. The result is a within-cell retrieval proxy. Ten official targets competed in each cell, the proxy used raw cosine and subtracted neither hub, and the product ranks chunks over the full catalogue with the applicable hub subtracted. It establishes no fluency, terminology or reader preference.

The semantic line used four stored vectors whose exact reads returned 240, 168, 479 and 592 courses. A representative-filter pushdown preserved set, order and scores on all four and was slower on every query. A centred SQL read also matched all four and ran in 0.4898 to 0.5023 seconds against 0.5699 to 0.6202 seconds for the exact read, a sample result that was not selected as a product change. A bounded exact NumPy read matched set and order with score differences below 3.1e-7, but its shared corpus read took 17.78 seconds of fixture read and 3.93 seconds of arithmetic for all four queries. On the approximate index, no candidate bound or `ef_search` value returned the exact set for all four vectors. Only candidate 512 with `ef_search` 512 reached recall 1.0000, and only for the first vector.

The lexical line fixed four query strings over two display languages and two activity scopes, which gives 16 cells per matcher. Under the fixture's default `en_US.utf8` collation, projection containment matched the Python substring set in all 16 cells and its order in 15. An ordering proof applied explicit `COLLATE "C"` to the three text keys and matched the full ordered identity lists in all 32 sampled cells, including the 61-result cell that had differed. Raw `lower()` mismatched the set on two inputs and trigram matching on three. The proof reran neither form, so those mismatches stand on these inputs. No SQL matcher, collation or index was selected, and the application matches in Python.

None of the three is an end-to-end search benchmark. No measurement joins the query embedding request to the database read, runs under concurrent load or measures a browser query through the merged search path. The [Search and translation experiments](/docs/experiments/search-and-translation/README.md) overview links the [translation and retrieval](/docs/experiments/search-and-translation/translation-and-retrieval.md), [semantic retrieval](/docs/experiments/search-and-translation/semantic-retrieval.md) and [lexical matching and collation](/docs/experiments/search-and-translation/lexical-matching-and-collation.md) reports.

### Recommendations

The recommendation experiments asked how recommendations score a basis, where a slow command spent its time, whether one centroid per course could replace the chunk-pair coverage step, and whether the same formula could cost less on float64 arrays and a narrower read. The line kept a formula-preserving change apart from a formula-changing approximation. The first had to return the same set, order and flags. The second could change the outcome, and its speed gain did not carry the earlier result.

The formula-preserving scorer returned the product retained set and order on all three fixed pools, with the same derived flags and all 27 adjacent exact tie pairs on the 50-course pool. Its wall median fell by 78.75 percent on the one-course pool, 86.27 percent on the 10-course pool and 91.81 percent on the 50-course pool, where 6.570340 seconds became 0.537979 seconds. The largest relatedness and score difference was 2.1316282072803006e-14 and the largest overlap difference 5.684341886080802e-14. The narrower read lowered its own wall median by 32.04, 30.57 and 26.31 percent. The two are separate measurements on separate timers, and their savings do not add to a command or request total.

The centroid approximation preserved set and order on the two smaller pools and changed both on the 50-course pool. It removed eight courses and changed 253 of the 311 common ranks, and its 58.85 percent scorer saving did not become a consistent composition saving. With both legs on the same read and arrays it was 1.35 percent faster on the one-course pool, 0.68 percent faster on the 10-course pool and 0.84 percent slower on the 50-course pool. The candidate chunk read dominated that leg at 4.05 seconds of 4.97 seconds. The candidate was dropped, and no measurement rates the relevance of the sets or ranks it changed.

The diagnosis found the time in the next-course stage on the small baskets and in overlap and result computation on the 49-course basket. Two request-local changes preserved every captured report and left complete recommendations at 1.644 to 2.760 seconds, and the target of about one second was not met. The [Recommendation experiments](/docs/experiments/recommendations/README.md) overview links the [scoring calibration](/docs/experiments/recommendations/scoring-calibration.md), [latency diagnosis and remediation](/docs/experiments/recommendations/latency-diagnosis-and-remediation.md), [centroid coverage](/docs/experiments/recommendations/centroid-coverage.md) and [vectorization and narrow reads](/docs/experiments/recommendations/vectorization-and-narrow-reads.md) reports.

### Graph and route algorithms

The graph and route experiments asked whether the exact minimum-credit route could be trusted on the full catalogue, what the calculation may claim after its allocation limit, why four graph roots failed to compile, and whether one report could carry the calculation and the drawing from two identities. The line kept four costs apart: compilation of the requirement tree into a solver structure, route search, drawing projection into display pieces and the serialized payload. The search allocation limit and the drawing allowance bound different costs, and neither bounds the whole request.

The [exact minimum route](/docs/backend/prerequisites/minimum-route.md#exact-by-default) attempt is bounded at 700,000 compact nodes and traces. A calculation past that bound abandons the exact attempt once and runs a single greedy pass, so the approximate totals it returns are not minima. One measured structure returns a marked size failure rather than a route. The parity comparison of the Python and TypeScript implementations found no difference in the measured scenarios and left four preparation failures uncompared. Equality there is empirical on one dataset and one seeded sample, not a proof about every structure.

The four roots that hit the preparation timeout or the address-space cap finish as complete graph commands in 2.36 to 3.01 seconds under the applied cycle cut. Route outcome and credits were preserved, and structure identity was not. A cycle-closing leaf that made the roots cheap was rejected because it changed the structure in 13 of 22 scenarios and turned five of 16 routes from exact to unresolved. Structural deduplication matched the route outcome, credits and course set in all 330 paired comparisons, changed occurrence evidence in 117, and showed no material exact gain, so it was not promoted.

The compact report keeps two identities. A fixture with an official `OR(a, b)` and an inferred `OR(b, a)` produces one drawn box but two ordered calculation pieces, because the drawing fingerprint sorts its children while the calculation identity keeps order. The report therefore joins an ordered calculation identity and an order-independent display identity through explicit support bindings. On the measured matrix it kept 104 of 110 cases identical and recorded six valid approximate cases with higher credit totals. It allowed 82 drawings and refused 28 at the [drawing limit](/docs/backend/prerequisites/prerequisite-graph.md#the-drawing-limit) of 500 elements, its maximum projection was 600.5 ms in the module-drawing pass, and it recorded no parity for unexpandable content. The [Graph and route algorithm experiments](/docs/experiments/graph-and-route-algorithms/README.md) overview links the [minimum-credit routes](/docs/experiments/graph-and-route-algorithms/minimum-credit-routes.md), [cyclic graph compilation](/docs/experiments/graph-and-route-algorithms/cyclic-graph-compilation.md), [structural route deduplication](/docs/experiments/graph-and-route-algorithms/structural-route-deduplication.md) and [compact graph identity and projection](/docs/experiments/graph-and-route-algorithms/compact-graph-identity-and-projection.md) reports.

### Runtime, storage and serving

The runtime, storage and serving experiments followed one stored row from the database to a response. They asked whether full-catalogue reads could select fewer columns and narrower identities without changing their output, what each read shape retains, whether a bounded cache shortens a repeated heavy call, what one served read costs and which worker count and limits keep the interactive path responsive, and what one capture produces.

The applied read projection returned byte-identical command outputs on the full catalogue. The paired memory result is a bounded descriptive read, which streams the rows in partitions, at 171.5 MB against 546.9 MB for the materialized read that holds every descriptive row, with 319 of 319 results and no membership, order, value or flag change. The bounded leg was about two seconds slower per recorded sample. The 546.9 and 171.5 MB values are process peaks on one fixed pool, not a serving measurement.

The first cache measurement recommended no facility. That was reversed. The experiment's 67.109 MB nominal byte bound and its probe average entry size gave 497 entries. The applied cache holds those 497 entries at 137,794 bytes per entry, a 68.484 MB accounted chunk term, and it was selected as a budget trade-off. Its measured median saving on a 432-result reproduction was 1.170300 seconds beyond a 0.112218-second warm spread. The benefit at the 200-course basis stayed within that basis's own spread, so the saving is confined to the 50-course basis. The retained chunk bytes measured 68.938 MB against 68.484 MB accounted, 0.663 percent above the term, and four accounted process shares of 632.344 MB fit the 1.074 GB aggregate.

Both worker-count comparisons recommended two worker processes. The selection chose four and reversed that recommendation, weighing the lower heavy-traffic probe tail at four against 6.5 percent more normal CPU per request and more memory. Admission is on with a saturated [heavy budget](/docs/backend/interfaces/admission-control.md#the-heavy-budget) of 40 core-seconds.

Four [load meters](/docs/reference/glossary.md#administration), each a rule that maps measured CPU or request activity to a load score or a load regime, were compared on 44 selected cells. The selected meter completed 49 heavy-alone calls against 42, 47 and 43 for the other three meters, and its worst mixed-traffic search p95 was 3,920 ms against 8,903 ms under the 10-second CPU meter, 9,448 ms under the 60-second CPU meter, both with a regime series, and 4,279 ms under the third CPU-only meter, which has no regime series. It did not restore the normal-only reference, each normal-traffic cell holds eight completed samples per search class, and one run per cell against a moving background load on the server is not a replicated causal estimate.

The memory proof ran the supervisor, the front router and the four worker processes together under one cgroup limit of 4.295 GB. That limit is the condition the proof ran under, not a product setting. A disposable kernel proof at 268.435 MB ended its child with SIGKILL rather than `MemoryError`, with both maximum-usage files at the limit and `memory.failcnt` at 0. The serving tree peaked at 0.410 GB during startup and light reads. No heavy load ran under the 4.295 GB limit, and the summed high-water marks of the six processes are not a simultaneous peak.

One timed capture and the two replays of a separate full-catalogue capture are the section's capture evidence, and the two captures are not compared on speed or scale. The [Runtime, storage and serving experiments](/docs/experiments/runtime-storage-and-serving/README.md) overview links the [curriculum capture and replay](/docs/experiments/runtime-storage-and-serving/curriculum-capture-and-replay.md), [read memory and serialization](/docs/experiments/runtime-storage-and-serving/read-memory-and-serialization.md), [descriptive chunk caching](/docs/experiments/runtime-storage-and-serving/descriptive-chunk-caching.md), [serving workers and admission](/docs/experiments/runtime-storage-and-serving/serving-workers-and-admission.md) and [serving load and admission limits](/docs/experiments/runtime-storage-and-serving/serving-load-and-limits.md) reports, and states the [serving load measurement method](/docs/experiments/runtime-storage-and-serving/serving-load-method.md).

## How the categories connect

Two questions recur. One asks whether a change returns the same result. The other asks whether the result is useful. The section keeps them apart. The recommendation scorer and the narrow read preserved their results and were applied, the scorer with the same set and order, the read with identical carriers. The centroid coverage, the approximate semantic index and the greedy route restart each changed an outcome, and each is reported as an approximation. The cycle cut preserved route outcomes on the measured commands but changed structure identity. No preservation measurement becomes a quality measurement, and no quality measurement licenses a change to the output.

Two measurements stand in for a property they do not measure. Judged support reports what a judge found in the supplied teaching text, not what the university requires, and it counts only the findings a model emitted. The translation result reports whether generated text retrieves its official counterpart within a cell, not whether a reader would accept the translation. Both informed a selection, and neither is a product-quality score.

Every saving stops at the boundary it was measured on. The recommendation scorer's 91.81 percent and the read's 26.31 percent are separate timers and do not add to a command or request, and neither is an HTTP measurement. The centred SQL read that was 0.08 to 0.13 seconds faster per query is a database read, not a search latency. The compact graph body was smaller on the four large cases it measured, but no browser parsed or rendered it. The cache saving is measured on a command, not through the front router and admission. The route parity is equal on one dataset and one machine, not a browser result.

The memory results are of different kinds and do not compose. 171.5 MB is a process peak on a fixed pool, 68.938 MB is retained cache bytes for one call sequence, 632.344 MB is four configured shares, 1.074 GB is the aggregate arithmetic, and 4.295 GB is the cgroup limit the memory proof ran under. The last is the only ceiling over the whole process tree, and no heavy load exercised it. A sum of these values would describe no measured process.

The section's evidence comes from many narrow cohorts rather than one representative benchmark. The cohorts include 60 translation cases, four stored query vectors, four lexical strings over 16 cells, 110 graph scenarios, 44 load cells with one run each and eight search samples per class in a normal-traffic cell. One case moves a ten-case translation cell's rate by 0.10, and one selected run per load cell does not estimate a distribution. The reports state those counts beside their results, and the section does not pool them.

The section also separates a measured candidate from an applied setting. The read projection, the 497-entry cache, four worker processes, admission on, the 40-core-second saturated budget and the load meter were selected and applied. The centroid coverage, structural deduplication, the approximate semantic index and the SQL matchers were not. The inference model and its no-filter policy were selected on held-out evidence before the full run. A measured value is not presented as the product's behavior unless the report states the selection.

## Open questions across the categories

Each question below is untested. None has a measurement in the section, and the category overviews carry further untested questions of their own.

- Human judgment and omissions. No agreement measurement exists between the blind judge and a human reader, no relevance rating covers a retained recommendation set or a changed rank, and no human rating covers translation fluency, terminology or adequacy. No measurement compares a published inferred set against the university's official prerequisite record, so an omitted true prerequisite is uncounted.
- Query input and language breadth. The semantic line has four stored vectors, the lexical line four fixed strings over two display languages, and the translation line 60 cases. None is a random sample of the catalogue's input, field, length or language mix, and no language outside Finnish and English has a measured result.
- A paired browser measurement that includes network and rendering. The search and translation comparisons measured query embedding and database reads separately. The [endpoint profile](/docs/experiments/runtime-storage-and-serving/endpoint-load-profiling.md) measured the HTTP search path, but no paired browser comparison joins those costs to browser parsing and rendering or tests the cache through the front router and admission.
- Controlled background, repeated runs and the memory ceiling. The load meter's cells are one selected run each against a moving background load on the server, and no heavy load ran under the 4.295 GB limit. A repeated fixed-mix run with a controlled background and a simultaneous process peak is unmeasured.
- A changed source or a repeated run. The full-catalogue inference run has no unchanged rerun and no changed-source recalculation, the catalogue has one timed capture, and the section has no second timed capture on the same machine and source. Every saved inference answer is one sample, so sampling variation is not separated from a model, prompt or packet effect.
